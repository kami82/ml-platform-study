### 주요 내용

**1. 시나리오 2: 대용량 데이터를 위한 경로 전달 (7.2.2)**

- 각 컴포넌트는 별도 파드에서 돌고 파드에는 메모리 한도가 있다. 값으로 큰 데이터를 넘기면 OOMKilled로 죽을 수 있으므로 **파일·디렉터리에 저장하고 경로를 넘긴다**.
- `Output[Artifact]` 파라미터는 KFP v2가 컴포넌트에 **쓸 수 있는 디렉터리 경로**(`.path`)를 주는 방식이다. KFP는 경로만 주므로 `os.makedirs(output.path)`로 디렉터리를 직접 만들고 그 안에 파일을 쓴다. 하류 컴포넌트는 `Input[Artifact]`로 같은 디렉터리를 받아 같은 파일명 패턴으로 읽는다.
- 파이프라인에서는 아티팩트 출력은 `task.outputs["이름"]`으로, 단순 반환값은 `task.output`으로 접근한다. 농담 생성 예제를 이 방식으로 바꾸면 `generate_joke`는 `jokes.txt`를 쓰고 `count_words`는 그 파일을 읽어 정수를 반환하며 `output_result`는 변경이 없다.
- 스터디 실습: UI에서 `count-words`의 Input Artifacts에 `generate-joke`의 Output Artifact 정보가 그대로 연결된 것을 확인했다.

**2. KFP v2 아티팩트 타입 (7.2.3)**

| 타입 | 용도 | 특징 |
| :--- | :--- | :--- |
| Dataset | 훈련/검증/테스트 데이터, 피처 세트, 전처리 결과, 분할 | `processed.metadata.update({...})`로 샘플 수·컬럼·처리 일시 같은 메타데이터 추적 |
| Model | 훈련된 모델, 체크포인트, 가중치, 사전 훈련 아티팩트 | 프레임워크 메타데이터 기본 지원, 학습 데이터·파라미터까지 리니지 추적 |
| Metrics | 성능·훈련·평가 지표 등 수치 측정값 | `metrics.log_metric('accuracy', v)`, 파이프라인 전반에서 비교·모니터링 |
| ClassificationMetrics | ROC 곡선, 혼동 행렬, 다중 클래스 지표 | `log_confusion_matrix(categories, matrix)`, 전용 UI 렌더링. SlicedClassificationMetrics는 데이터 슬라이스별 적용 |
| HTML | 인터랙티브 시각화, 리치 포맷 보고서, 대시보드 | `report.path`에 HTML을 쓰면 KFP UI에서 직접 표시 |
| Markdown | 문서, 간단한 보고서, 모델 카드, README, 훈련 요약 | UI에서 렌더링되고 일반 텍스트로도 읽기 편함 |
| Artifact | 커스텀 타입, 범용 파일, 설정 파일, 중간 결과물 | 다른 타입에 맞지 않을 때의 기본 타입. 메타데이터 추적은 동일 |

- 모든 타입이 내장 메타데이터 추적과 표준화된 스토리지 처리를 제공하므로, 타입을 맞춰 쓰면 데이터 리니지와 모델 출처 추적이 되는 유지보수 가능한 파이프라인이 된다.

**3. 객체 탐지 데이터 준비 (7.3.1)**

- **YOLO 입력 형식**: 설정 YAML에 `path`(루트), `train`/`val`/`test`(이미지 경로), `names`(클래스 인덱스 → 이름, 0부터, 여기서는 `id_card` 하나). 레이블은 이미지 폴더 옆 `labels/`에 같은 이름(`images/id0042.png` ↔ `labels/id0042.txt`)으로 둔다. 구현마다 설정·폴더·명명 규칙이 다르니 문서를 먼저 확인할 것.
- **데이터셋**: MIDV-500(신분증·여권·운전면허증 등 50종 문서의 동영상 클립 500개, https://github.com/fcakyon/midv500). 책은 신분증만 남기고 Ultralytics YOLO 형식으로 변환해 Box URL로 제공한다(약 10GB).
- **다운로드 컴포넌트** 4단계: (1) `requests.get(stream=True)` + tqdm으로 청크 다운로드, (2) `tarfile.open(..., 'r:gz').extractall()`, (3) boto3로 MinIO 버킷 생성·업로드(책 기본 자격 증명은 프로덕션에서 반드시 변경, Vault 사이드카 권장), (4) 모든 import를 함수 안에 넣고 `@dsl.component(packages_to_install=[...], base_image="python:3.11")`로 감싼다. KFP v2에서는 `Output[Dataset]`에 바로 압축을 풀면 (3)의 수동 업로드가 필요 없다.
- **컴포넌트 간 데이터 전달**: 데이터셋 10GB에 컴포넌트 5개면 복사 방식은 50GB를 받게 된다. 대신 `Output[Dataset]` 경로에 풀어 두고 하류는 `input_dataset.path`로 접근한다. 파일이 파드 메모리보다 크면 OOM이 나므로 원격 위치를 가리키게 한다.
- **분할 컴포넌트**: `packages_to_install=["scikit-learn"]`으로 `train_test_split`을 쓴다. 두 파티션만 나누므로 75/15/10은 두 번 나눈다. 1차 `test_size=1-0.75`, 2차 `test_size=0.10/(0.10+0.15)`. 같은 `random_state`로 재현성 확보. 분할마다 `Output[Dataset]` 하나씩(train/validation/test), 각 안에 `images/`·`labels/`를 만들고 `shutil.copy2`로 복사한다.
- **검증 컴포넌트** `output_file_contents`: `Input[Dataset]`을 받아 `os.walk`로 트리를 들여쓰기 출력하는 임시 컴포넌트. 디버깅과 배치 확인용.
- **전체 파이프라인**: `download_dataset()` → `split_dataset(input_dataset=download_op.outputs["output_dataset"])` → `output_file_contents(dataset=split_op.outputs[...])`. 출력을 입력으로 연결하면 KFP가 순서를 자동 보장하므로 `.after()`가 필요 없다. 의존성은 파이프라인이 아닌 컴포넌트 수준(`packages_to_install`)에 둔다. `python data_prep_pipeline.py`로 컴파일하면 `dataprep_pipeline.yaml`이 생긴다.
- **업로드·실행**: UI Upload pipeline(zip 또는 YAML) → 그래프 확인 → Create Run. Experiment는 실행을 묶는 단위로 서로 다른 파이프라인 실행이 섞여도 된다. 일회성 대신 반복 실행도 가능. 함수 시그니처의 파라미터가 Run 폼에 자동 채워진다. 저자 환경에서 약 30분.

**4. 영화 추천 데이터 준비 (7.3.2)**

- **MovieLens 25M**: 그룹렌즈(미네소타대) 제공, 사용자 16.2만 명의 평점 2,500만 건·태그 100만 건·영화 6.2만 편. 이용 약관 준수 필요, 공개 재배포 불가.
- 컴포넌트 6개: 다운로드 → 압축 해제(ratings.csv, movies.csv만) → CSV→Parquet(같은 컴포넌트를 두 번 병렬 호출) → 분할(입력 Parquet, 출력은 Parquet 3개가 든 폴더) → MinIO 업로드(파일·폴더 모두 처리, `upload_file_name`으로 KFP가 자동 부여한 경로명을 원하는 이름으로) → QA. 실제 배포에서는 전달 오버헤드를 줄이려고 여러 컴포넌트를 합치지만 책은 데이터 전달 시연을 위해 분리한다.
- **Parquet**: 테이블 형식 데이터에 열 기반 저장으로 샤딩·작은 크기·조회 성능 이점. pandas + fastparquet로 변환(시연용, 샤딩·최적화 없음).
- **컨테이너화된 파이썬 컴포넌트**: `@dsl.component(target_image="...")`를 주면 의존성을 빌드 시점에 설치한 이미지를 만들어 푸시하고, 런타임 pip 설치 없이 바로 실행된다. 경량 파이썬 컴포넌트(런타임 pip)와 완전한 컨테이너 컴포넌트 사이에 위치하며, 함수 밖 모듈 import도 가능해진다. 도커 데몬·API 소켓·유닉스가 필요하고 `packages_to_install`을 쓸 때 권장된다.
- **QA 컴포넌트**: PyArrow `fs.S3FileSystem`으로 MinIO의 train Parquet을 직접 열어 열 4개, 행 수 ≥ 전체의 75%를 `assert`한다. 사후 디버깅보다 생성 단계에서 가정을 검증하는 것이 낫다. 후속 장에서는 PyArrow로 훈련에 직접 스트리밍한다.
- **실행 순서 수동 지정**: `qa_data(...).after(u1).after(u2)`처럼 데이터 의존이 없는 태스크는 `.after()`로 묶는다. 모든 태스크에 `set_caching_options(False)`.
- **SDK 업로드**: 노트북이 클러스터 안에 있으면 `kfp.Client()`에 자격 증명·엔드포인트 없이 접속된다(시작 시 주입된 환경 변수). 밖에서는 엔드포인트를 지정해야 하고, 다중 사용자 환경이면 RBAC용 서비스 계정 자격 증명이 필요하다.
- **7.4 요약**: ML 워크플로는 데이터 가까이에서 돌고 GPU에 임시 접근이 필요하다. 노트북은 파이프라인과 같은 클러스터·베이스 이미지를 공유한다. 컴포넌트는 함수에서 만들고 import는 함수 안에, 서드파티는 `packages_to_install`로. 컴파일 YAML에는 함수 정의와 입출력 직렬화 보일러플레이트가 들어 있고 UI·SDK로 업로드·실행하며 로그를 실시간으로 본다.

**5. 책 vs 스터디 실습 환경**

| 구성 요소 | 책 | 스터디 실습 |
| :--- | :--- | :--- |
| 실행 환경 | Kubeflow Notebooks에서 `kfp.Client()` | 리모트 kind `book-env`(KFP 백엔드 2.4.1 / SDK 2.9.0), 노트북 없이 venv에서 `kfp.Client(host=...)` + `submit.py`(제출·대기·`[ch07]` 마커 로그만 출력) |
| 객체 탐지 데이터 | `MINIDATA/` 기준 코드 | 책 URL의 tar 최상위는 `DATA/`뿐(`tar tzv`로 확인). `BASE_PATH`를 `DATA`로 바꾸지 않으면 glob이 비어 `ValueError` |
| 분할 코드 | images/labels를 따로 glob 후 정렬 없이 `train_test_split(images, labels)` | 파일명(stem) 기준으로 짝을 맞춰 정렬 후 분할. `paired=5609 only_img=0 only_lbl=0`, 분할별 불일치 0, 분할 간 중복 없음 |
| 다운로드 | `chunk_size=1024`, tqdm 기본 | 1MiB 청크 + `tqdm(mininterval=30)`. 10GB를 1KiB씩 쓰면 1,000만 회 반복 + 로그 폭주 |
| 검증 출력 | train 전체 트리 출력 | validation 분할만, 디렉터리당 5개 + 개수, 이미지·라벨 짝 검사 추가 |
| 책 listing 7.23 | `split_op.outputs["x_val_output"]` | 실제 출력 이름은 `train_dataset`/`validation_dataset`/`test_dataset`이라 그대로면 컴파일 오류 |
| 오브젝트 스토리지 | MinIO | KFP standalone의 "minio"는 실제로 **SeaweedFS 3.85**. 기본 인자 `-volume.max=100 -master.volumeSizeLimitMB=64`라 한도가 약 6.4GB |
| 영화 추천 코드 | `target_image="mlsysfromscratch/..."`, 책 listing 7.26·7.28·7.30 | 저장소 코드에는 `target_image` 없음. 책 listing의 함수명 중복·`os` 누락·괄호 오류는 저장소 코드로 대체. `client.pipeline_uploads.upload_pipeline(name=)`은 v1 API, SDK 2.9는 `upload_pipeline(..., pipeline_name=)` |
| 이미지 레지스트리 | 공개 레지스트리 | 6장에서 만든 클러스터 내부 Docker 레지스트리. 호스트에서는 port-forward 포트로 push하고 노드는 `127.0.0.1:5000/...`으로 pull |

- **실습 메모 (7.3.1 객체 탐지, 약 35분)**
  - 다운로드 파드 약 25분(10.28GB 다운로드 14분 + 압축 해제 + MinIO 업로드), split 약 9분, 검증 1분. 압축 해제 결과 16.9GB·파일 11,218개(`.tif` 5,609 + `.txt` 5,609). 분할은 train 4,206 / validation 841 / test 562(75.0/15.0/10.0%), MinIO 기준 12.68 / 2.53 / 1.69GB.
  - **첫 실행은 업로드 중 500으로 실패**. 원인은 SeaweedFS 볼륨 슬롯 100개가 모두 찬 것(`No writable volumes and no free volumes left`). 호스트 디스크나 PVC 크기와 무관하다. Deployment `minio`의 인자를 `-volume.max=1000`으로 올려(Recreate, 데이터는 PVC에 유지) 재실행 성공.
  - `create_run_from_pipeline_package()`는 컴파일 YAML을 run 요청에 실어 보내는 일회성 실행이라 Runs·Experiments에만 보이고 Pipelines 목록에는 등록되지 않는다. 등록하려면 `upload_pipeline` 후 버전으로 실행해야 한다.
  - `shutil.copy2`로 분할마다 복사하므로 원본 16.9GB가 한 번 더 저장되어 MinIO에 약 2배(33.8GB)가 쌓인다. `boto3`는 `packages_to_install`에 있지만 코드에서 쓰지 않는다(책 3단계의 흔적). `base_image`를 생략한 컴포넌트는 SDK 기본 `python:3.8`로 돈다.
  - 아티팩트 경로는 `mlpipeline/v2/artifacts/<파이프라인>/<run_id>/<태스크>/<uuid>/<출력명>/...`이고 `aws --endpoint-url ... s3 ls`로 직접 확인했다.
- **실습 메모 (7.3.2 영화 추천, 약 11분)**
  - A(경량)와 B(`target_image` 컨테이너화) 모두 성공. 분할은 train 18,750,071 / val 3,750,014 / test 2,500,010(합 25,000,095), movies 62,423행, QA 통과. B가 같은 `datasets/ml-25m/` 경로를 덮어써 현재 파일은 B 결과다.
  - 원본 수정: `split_dataset`의 `ratings_df.user_id.max()`·`item_id.max()` 삭제(컬럼은 `userId/movieId`라 `AttributeError`, 값도 미사용). `put_to_minio`의 예외를 `except Exception`으로 넓힘(u1·u2가 동시에 `create_bucket` 호출). 책은 `.after(u1).after(u2)`, 저장소는 `.after(u2)`만.
  - B는 `kfp component build . --component-filepattern ... --no-push-image`로 이미지 1개(2.51GB)를 빌드한다. Dockerfile은 자동 생성(`FROM python:3.11` → runtime-requirements 설치 → `pip install kfp` → `COPY . .`).
  - **발견 1**: SDK 2.9.0은 `target_image`가 있어도 컴파일 command에 `pip install '<packages_to_install>'`을 그대로 넣는다(`kfp` 자동 설치만 빠짐). 책의 "런타임 설치 없음"과 다르다. **발견 2**: 이미지 하나에 6개 컴포넌트 패키지가 합쳐져 pyarrow와 fastparquet가 같이 들어가고, pandas `to_parquet(engine="auto")`가 pyarrow를 먼저 고르므로 A(fastparquet, `index` 열 맨 앞)와 B(pyarrow, `__index_level_0__` 맨 뒤)의 Parquet 스키마가 다르다. 뒤 장의 읽기 코드는 인덱스 열 이름에 의존하면 안 되고 `index=False`로 쓰는 것이 낫다.
  - 컴포넌트별 시간(A): download 363초(외부 네트워크), unzip 24, ratings 변환 52, movies 변환 32, split 96, 업로드 21·20, QA 27초. 각 단계가 pip를 반복 설치하므로 B가 QA 10초·movies 변환 20초로 빨랐다. 노드는 `IfNotPresent`로 태그를 캐시하므로 코드를 고치면 태그를 올려야 한다.
  - 옵션 실습: QA 컴포넌트에 `Output[Markdown]`(분할별 행 수·비율, PASS/FAIL 표, 평점 분포)과 `Output[Metrics]`(스칼라 8개)를 추가해 UI Visualization 탭에서 확인. `split_dataset`의 `to_parquet`에 `compression_level=1`을 주면 B의 split이 344초 → 32초로 10.8배 빨라졌다.
- 도전과제: KCD(KFP, Notebook, TensorBoard 등) 설치 환경에서 실습 따라해 보기 / KFP v2 다양한 아티팩트 타입을 쓰는 컴포넌트 작성 / 외부 공개 데이터셋(Google Dataset Search, Hugging Face, OpenML, Kaggle, UCI, SNAP, AWS Open Data, data.gov 등)을 골라 다운로드·준비 KFP 작성·실행.

# CH8. 모델 훈련 및 검증 1부 (YOLOv8 훈련 · 컨테이너 컴포넌트 · 검증 지표)

### 한 줄 요약

8장은 그림 1.4의 4단계(훈련)와 5단계(평가)를 7장 데이터 준비 파이프라인 뒤에 붙인다. 커스텀 데이터셋용 YOLO 설정 YAML을 만들고 Ultralytics `YOLO('yolov8n.pt').train()`으로 훈련하는 스크립트를, apt 패키지까지 설치하는 `@dsl.container_component`로 감싸 heredoc으로 주입한다. 검증은 Ultralytics 이미지를 `base_image`로 쓰는 `@dsl.component`에서 `model.val()`로 mAP를 구해 `Output[Metrics]`로 남기고, 산출물 `best.pt`를 내려받아 기본 모델과 추론을 비교해 "신뢰하되 검증"한다.

<br>

### 주요 내용

**1. 8장의 위치와 목표**

- 다루는 내용: 모듈형 훈련 컴포넌트 설계, 추적 프레임워크에 지표·아티팩트 수집, 파이프라인에 훈련·검증 컴포넌트 추가, 훈련·평가 데이터 접근 방법.
- 노트북이 아니라 컴포넌트로 훈련하는 이유: 소스 관리에서 버전 추적, 환경이 달라도 일관 실행, 데이터 준비 파이프라인과 통합, 체계적 모니터링·평가.
- 훈련 컴포넌트의 역할 세 가지: train/val/test 이미지·라벨을 폴더에 받기, 데이터셋 설정 만들기, 훈련·평가 실행. Ultralytics가 훈련·평가 대부분을 대신하지만 코드는 얼마든지 커스터마이징할 수 있다.

**2. 커스텀 데이터셋으로 YOLO 훈련 (8.1.1~8.1.2)**

- 설정 딕셔너리 `{'path', 'train', 'val', 'test', 'names': {0: 'id_card'}}`를 `yaml.dump`로 `custom_data.yaml`에 쓴다. 레이블은 `train/labels`처럼 이미지 옆 디렉터리에 둔다. 다른 객체를 탐지하려면 `names`에 클래스를 추가한다.
- 프로덕션 훈련은 훈련 효율(배치·학습률), 리소스 활용(아키텍처 선택), 성능 요구(정확도 vs 훈련 시간)의 균형이다.
- `model = YOLO('yolov8n.pt')`로 사전 훈련 모델을 받고 `model.train(data, imgsz=640, epochs, batch, name, project)`를 호출한다. `imgsz`는 정사각형 리사이즈 크기(비정사각형은 레터박스), 클수록 정확도↑·메모리·시간↑. `project` 경로에 가중치, 혼동 행렬, PR 곡선, 훈련·검증 추론 샘플이 에포크마다 자동 저장된다.
- **아키텍처 선택**: YOLOv8n(나노)은 빠르고 메모리가 적어 에지·실시간용, 큰 모델은 정확하지만 자원이 더 든다. 감시 카메라면 속도, 자율주행이면 정확도를 우선한다. 나노로 시작하는 이유는 컴퓨팅 절약, 실현 가능성 검증, 반복 개선.
- **하이퍼파라미터(표 8.1)**

| 키 | 기본값 | 설명 · 조정 시 고려 |
| :--- | :--- | :--- |
| model / data | 없음 | 모델 파일(`yolov8n.pt`), 데이터 YAML. 목적에 맞는 아키텍처, 충분히 레이블된 데이터 |
| epochs | 20 | 많을수록 좋아지지만 시간 증가 |
| batch | 4 | 늘리면 빠르지만 GPU 메모리 제약과 그레이디언트 업데이트 감소. -1이면 AutoBatch |
| imgsz | 640 | 정밀한 위치 파악이 필요하면 고해상도 |
| save / project / name / exist_ok | True / 없음 / 없음 / False | 체크포인트·예측 저장, 프로젝트·실험 이름, 기존 실험 덮어쓰기 여부 |
| pretrained | True | 사전 훈련 모델로 시작할지, 처음부터 할지 |
| optimizer | auto | SGD·Adam·AdamW 등. auto는 반복이 1만 회를 넘으면 SGD, 아니면 AdamW |
| verbose / val | False / True | 상세 출력, 훈련 중 검증 |

**3. 시스템 의존성을 위한 컨테이너 컴포넌트 (8.1.3)**

- Ultralytics 이미지에서 `ImportError: libGL.so.1`이 날 수 있는데 `apt-get install libgl1-mesa-glx`가 필요하다. `@dsl.component`는 파이썬 패키지만 설치하므로 `@dsl.container_component` + `dsl.ContainerSpec`으로 이미지·명령·인수를 직접 지정한다. Dockerfile 없이 파이썬 코드 안에 유지하는 대신 정의가 길어진다.
- **1단계 훈련 스크립트**: `parse_args()`로 `--train-path/--val-path/--test-path/--epochs/--batch/--model-name/--model-output/--data-yaml`를 받고, `main()`이 `data.yaml`을 쓰고 `model.train(project=os.path.dirname(args.model_output), name=args.model_name)` 후 `weights/best.pt`를 `args.model_output/best.pt`로 복사한다. 독립 실행 가능.
- **2~3단계 ContainerSpec**: `image='python:3.11-slim'`, `command=['bash','-c']`, `args`의 첫 요소가 f-string 셸 스크립트다. apt로 `libgl1-mesa-glx libglib2.0-0` 설치 → pip로 ultralytics·torch·opencv-python-headless·minio·tqdm·pyyaml 설치 → `cat << 'EOF' > /train.py`로 `TRAINING_SCRIPT` 문자열을 파일에 쓰고 → `python3 /train.py --train-path "$0" ...`로 실행. 나머지 `args` 요소(`train_dataset.path`, `epochs`, `model_output.path` 등)가 Bash 위치 파라미터 `$0..$7`에 매핑되어 KFP 타입 시스템과 스크립트 CLI를 잇는다.
- 시그니처: `epochs: int, batch: int, yolo_model_name: str, train/validation/test_dataset: Input[Dataset], model_output: Output[Model], data_yaml: Output[Artifact]`. 사용법은 `@dsl.component`와 완전히 같다.

**4. 검증 컴포넌트와 파이프라인 (8.1.4~8.1.6)**

- 검증의 목적: 성능 저하 조기 감지, 세그먼트별 성능 파악, 배포 의사결정, 과거 성능 기록. 핵심은 KFP의 **지표 출력**(마크다운·플롯·원시 값).
- requirements.txt로 전부 설치하려다 **의존성 지옥**(TF vs PyTorch vs OpenCV 버전 충돌)에 빠지기 쉽다. 미리 패키징된 `ultralytics/ultralytics:8.0.194-cpu`를 `base_image`로 쓰고 나머지(`minio`, `tqdm`)만 `packages_to_install`로 추가한다.
- `validate_model(data_yaml: Input[Artifact], model: Input[Model], validation_dataset: Input[Dataset], metrics: Output[Metrics])`: `YOLO(model.path/best.pt)` → `model.val(data=data_yaml.path/data.yaml, imgsz=640, batch=1)` → `metrics.log_metric("map50-95"/"map50"/"map75", ...)`. 아티팩트 타입 4종(Artifact·Model·Dataset·Metrics)이 컴포넌트 간 데이터 흐름과 의존성을 KFP가 관리하게 한다.
- 파이프라인: download → split → `train_model(train/validation/test_dataset=split_op.outputs[...])` → `validate_model(data_yaml=train_op.outputs["data_yaml"], model=train_op.outputs["model_output"], validation_dataset=split_op.outputs["validation_dataset"])`. split과 validate 사이에도 연결선이 생긴다. 컴파일 결과는 `training_and_validation_pipeline.yaml`.
- 실행: Run 파라미터는 파이프라인 기본값으로 미리 채워진다. 저자 환경에서 1 에포크 약 1시간, 학습 목적에는 1 에포크로 충분. Ultralytics는 모델 요약(계층·파라미터 수), 훈련 설정, 데이터셋 정보(손상 이미지 수), 에포크별 손실·mAP, 단계당 시간·남은 시간을 출력한다. 결과는 Run output 탭(지표), Output artifacts(원시 값), Pipeline Overview(실행별 지표 목록)에서 본다.

**5. 모델 아티팩트 검증 (8.1.7)**

- 자동 검증 외에 수동 확인은 특정 케이스 검증, 예상 밖 출력 디버깅, 이해관계자 시연, 파이프라인 신뢰 구축에 쓰인다. "신뢰하되 검증하라". 넘겨받은 모델이 한참 뒤에야 동작하지 않는다고 밝혀지는 일이 실제로 있다.
- 기본 `yolov8n.pt`로 `samples/` 이미지를 추론(`result[0].plot()` → `cv2.imshow`)하면 얼굴을 person으로, 신분증을 book으로 낮은 신뢰도(0.28)로 분류하지만 경계 상자는 대체로 맞다. 신뢰도는 0~1 점수이고 애플리케이션에 따라 불확실한 예측을 걸러내는 데 쓴다.
- Output artifacts에서 프로젝트 tar를 받아 `best.pt`로 바꿔 실행하면 1 에포크만으로도 id_card로 올바르게 분류한다(상자는 아직 거칠다). 약 5 에포크면 상자가 카드를 완전히 덮고 신뢰도도 좋아진다. 에포크 추가로 정확도·신뢰도·견고성이 개선되지만 필요한 수는 데이터 복잡도와 요구사항에 달렸다.
- Ultralytics는 검증 성능이 가장 좋은 가중치를 `best.pt`로 저장한다. 100 에포크를 돌려도 4번째 결과일 수 있고, 3 에포크만 돌리면 그중 최선일 뿐 충분히 훈련되지 않았을 수 있다. "충분한" 에포크가 핵심.
- 모델이 동작하면 자동화를 고민한다. 신뢰도가 임계값 이상인지, 경계 상자 좌표가 적절한지를 허용 오차를 두고 프로그래밍으로 검증한다. 하이퍼파라미터 조정은 반복 과정이라 최소 집합에서 시작해 수렴하지 않으면 학습률·배치·에포크를 바꾼다.
- **8.2 요약**: 데이터를 모델까지 가져오는 방법은 여러 가지이며 버전 관리·계보를 지원해야 한다. 아키텍처는 요구사항과 제약의 트레이드오프로 고른다. "로컬 접근은 최선이 아니다"라고 가정하고 데이터 접근·전달을 설계한다. 지표의 가시성이 팀 단위 운영의 핵심이고, 출력 가중치에 간단한 sanity test를 빠르게 돌릴 수 있어야 한다.

**6. 책 vs 스터디 실습 환경**

| 구성 요소 | 책 | 스터디 실습 |
| :--- | :--- | :--- |
| 하드웨어 | K8s 클러스터, 1 에포크 약 1시간 | CPU 16코어·GPU 없음. 1 에포크 train 태스크 25분(입력 17GB 수신 + 설치 + 학습 21분 + 업로드) |
| 베이스 이미지 apt | `libgl1-mesa-glx` | `python:3.11-slim`은 Debian 13(trixie)이라 설치 후보 없음 → `libgl1`로 교체 |
| pip | `ultralytics`, `torch` 버전 미고정 | CPU 휠 인덱스(`--index-url .../whl/cpu`) + `ultralytics==8.4.207`, `torch==2.15.0` 고정 |

# CH9. 모델 훈련 및 검증 2부 (PVC 데이터 관리)

### 한 줄 요약

9장은 훈련·평가 단계를 데이터 관리, 실험 추적, 모델 버전 관리 인프라로 보강한다. 4주차는 9.1만 다룬다. `kfp[kubernetes]`의 `CreatePVC`·`mount_pvc`·`DeletePVC`로 파이프라인 전용 PVC를 만들어 모든 컴포넌트가 `/data`를 공유하게 하면 데이터셋을 한 번만 받고, download·split·train·validate 코드에서 MinIO 업로드·다운로드와 InputPath 인수가 사라진다. 대신 데이터 의존이 없어지므로 `.after()`로 순서를 명시해야 한다. 9.2 TensorBoard와 9.3 영화 추천기는 5주차에 진행한다.

<br>

### 주요 내용

**1. 9장의 위치와 9.1 배경**

- 다루는 내용: K8s 퍼시스턴스 볼륨으로 데이터셋 저장·조회, MLflow·TensorBoard로 훈련 추적·시각화, 리니지와 실험 추적의 중요성.
- 7·8장 방식의 한계: 전체 데이터셋을 download 컴포넌트가 받고, train 컴포넌트가 분할본을 다시 받고, validate 컴포넌트가 검증 분할을 또 받는다. 컴포넌트 간 중복 다운로드, 비효율적 스토리지, 제한된 공유.
- MinIO는 POSIX 파일시스템이 아니라 복사·이동이 번거롭다. PVC는 파이프라인 컴포넌트 전반에 지속적·공유 스토리지를 주어 한 번 받아 재사용하고, 컴포넌트 간 공유하고, 스토리지를 효과적으로 관리하게 한다. MinIO 방식이 쓸모없어지는 것은 아니며 문제·모델·인프라 제약에 따라 고른다.
- `pip install kfp[kubernetes]`로 KFP에서 K8s 고유 기능에 접근한다.

**2. PVC로 파이프라인 리팩터링 (9.1.3~9.1.7)**

- **VolumeOp 생성 (9.1.3)**: 파이프라인 정의 안에서 `kubernetes.CreatePVC(pvc_name, access_modes=['ReadWriteOnce'], size='1Gi', storage_class_name='local-path')`. 대부분의 스토리지 클래스가 ReadWriteOnce를 지원한다. 스토리지 클래스 이름은 클러스터마다 다르다. 모든 컴포넌트가 `createpvc`에 의존한다(그림 9.2).
- **download_op (9.1.4)**: `kubernetes.mount_pvc(download_op, pvc_name=pvc_name, mount_path='/data')`. 함수는 tar를 `/data/DATASET`에 바로 푸는 것으로 끝나 MinIO 코드와 디렉터리 생성이 사라진다.
- **split_op (9.1.5)**: 마운트는 같고 `.after(download_op)`를 명시해야 한다. 아티팩트 때는 데이터 의존으로 순서를 추론했지만 이제는 없기 때문. `/data/DATASET/MINIDATA/images|labels`를 glob해 분할하고 `/data/{train,test,val}/{images,labels}`로 복사한다.
- **train_op (9.1.6)**: `.after(split_op)` + 마운트. `train_model` 시그니처에서 `Input[Dataset]` 3개가 사라지고 `TRAINING_SCRIPT`의 `parse_args`에서 경로 인수가 빠지며 `data.yaml`은 `/data/train/images` 같은 고정 경로를 쓴다. 남은 것은 YAML 생성과 훈련뿐.
- **validate_op (9.1.7)**: `data_yaml`·`model`은 여전히 train_op의 출력으로 받고 `.after(train_op)` + 마운트. `validation_dataset` 입력이 사라지고 `base_image`는 `ultralytics/ultralytics:8.3.56-cpu`. PVC로 코드 양이 크게 줄고 데이터 저장이 단순해진다(그림 9.3).

**3. 책 vs 스터디 실습 환경**

| 구성 요소 | 책 | 스터디 실습 |
| :--- | :--- | :--- |
| 라이브러리 | `kfp[kubernetes]` | `kfp==2.9.0` 고정으로 `kfp-kubernetes 1.5.0`만 추가(kfp가 올라가 컴파일 결과가 바뀌는 것 방지). 저장소 requirements는 `kfp==2.11.0` |
| 스토리지 클래스 | `local-path` | 이 클러스터에는 없는 이름. `standard`(`rancher.io/local-path`, `WaitForFirstConsumer`, reclaim `Delete`)로 교체 |
| 데이터 | MINIDATA(약 1.23GB) | 7·8장(10.28GB, `DATA/`)과 다른 작은 데이터. 압축 해제 2,289개, 이미지·라벨 쌍 570개 → train 427 / val 85 / test 58. 8장 mAP와 비교 불가 |
| TensorBoard | Kubeflow 사이드바 → TensorBoards | kind에는 CRD·컨트롤러·대시보드가 없어 불가. PVC를 마운트한 Deployment + port-forward로 대체 예정(5주차) |

| 영화 데이터 | 전량 | `negative_sampling`이 사용자 16만 × 아이템 5.6만, 학습이 epoch당 58만 iteration × 30이라 CPU로 비현실적. 책 표 9.1·9.2도 6,400 샘플로 실험. 사용자 부분집합으로 소형 데이터셋을 만들 예정(5주차) |

- **실습 메모 (A0 PVC 시험)**
  - 동적 이름(`pvc_name_suffix="-smoke"`, `pvc.outputs["name"]`으로 마운트, `DeletePVC`)과 고정 이름(정적 문자열로 마운트, `DeletePVC` 없음) 두 파이프라인 모두 성공. 쓰기 태스크가 쓴 파일을 읽기 태스크가 같은 PVC에서 읽었다. 고정 이름은 재실행해도 `createpvc`가 `AlreadyExists` 없이 성공(기존 PVC 재사용으로 보임). `.after(pvc)`를 생략해도 이번엔 문제 없었지만 항상 보장되는지는 미확인.
  - PVC 이름은 `<argo workflow 이름>-<suffix>`로 생성되고 `WaitForFirstConsumer`라 첫 파드가 뜰 때 `Bound`된다. local-path PV의 실제 위치는 kind 노드 안 `/var/local-path-provisioner/pvc-<uid>_<ns>_<name>/`.
  - **발견**: `DeletePVC`는 PVC를 `Terminating`으로만 만든다. 완료된(`Succeeded`) 파드가 PVC를 참조하는 동안 `pvc-protection` finalizer가 풀리지 않고, 파드를 지우면 PVC·PV·노드 디렉터리가 바로 사라진다. 실제 삭제 시점은 워크플로 파드가 정리될 때이며 책 9.3.1의 `TTL_SECONDS_AFTER_WORKFLOW_FINISH`와 관련 있을 것으로 추정(미확인).
  - 컴파일 YAML은 KFP 스펙 뒤에 `---`로 구분된 `platforms.kubernetes` 섹션에 `pvcMount`가 들어간다. `createpvc`·`deletepvc` 실행자는 `argostub/createpvc` 스텁 이미지다.
- **실습 메모 (A1 책 파이프라인, A2 재사용)**
  - A1 `yolo-pvc`: `CreatePVC(10Gi, standard)` → download → split → train(컨테이너 컴포넌트) → validate, 모두 `/data` 마운트. 시간: createpvc 4초, download 89초, split 31초, train(1 에포크) 172초, validate 121초(이미지 첫 pull 포함), 전체 473초. 1 에포크라 mAP50 4e-4로 사실상 학습 전.
  - 막힌 점: (1) 파이프라인 이름이 길면 `createpvc` driver가 `pods "...drive" not found`로 실패 → 이름을 짧게(파드 이름 63자 절단 가설, 미확인). (2) 실패한 run이 Pending PVC를 남겨 다음 run이 `already exists`, 삭제도 실패 파드 때문에 `Terminating`에서 멈춤 → 실패 workflow를 지우고 PVC 이름 변경. (3) 컴포넌트 기본 인자가 모듈 상수를 참조하면 경량 컴포넌트는 함수 본문만 직렬화하므로 `NameError` → 리터럴로 교체.
  - A2 `yolo-a2`: 기존 PVC를 마운트해 train → validate만 실행. 첫 시도는 `yolov8n.pt` GitHub 다운로드 504로 실패해 `set_retry(2, 30s)` 추가 후 성공. download 89초 + split 31초 = 120초 생략. 단 A1의 validate에는 이미지 첫 pull이 섞여 단순 비교는 안 된다.
  - 비교: PVC 재사용은 복사가 0이고 데이터 버전이 파이프라인 밖(PVC)에 있다. importer/아티팩트 방식은 MinIO 경로로 계보가 남지만 단계마다 업로드·다운로드가 든다.
- 5주차 예정: 9.2 TensorBoard로 훈련 추적, 9.3 영화 추천기 프로젝트(MLflow 연동).

| 개념 | 설명 |
| :--- | :--- |
| `kfp[kubernetes]` / kfp-kubernetes | KFP 파이프라인에서 PVC 등 K8s 고유 기능을 쓰는 확장 패키지 |
| `kubernetes.CreatePVC` | 파이프라인 안에서 PVC를 만드는 태스크(VolumeOp). `pvc_name` 또는 `pvc_name_suffix`, `access_modes`, `size`, `storage_class_name` |
| `kubernetes.mount_pvc` | 태스크에 PVC를 `mount_path`로 마운트. PVC 이름은 정적 문자열 또는 `pvc.outputs["name"]` |
| `kubernetes.DeletePVC` | 파이프라인 끝에서 PVC 삭제. 참조 파드가 남아 있으면 `Terminating`에 머묾 |
| ReadWriteOnce | 노드 하나에서 읽기·쓰기 마운트. 대부분의 스토리지 클래스가 지원 |
| StorageClass | PV를 동적으로 만드는 프로비저너 정의. 이름은 클러스터마다 다름(`local-path`, `standard`) |
| WaitForFirstConsumer | 파드가 스케줄될 때 PV를 바인딩하는 모드 |
| reclaim Delete | PVC를 지우면 PV와 데이터도 삭제 |
| POSIX 파일시스템 | 일반 파일 복사·이동이 되는 파일시스템. MinIO(오브젝트 스토리지)는 아님 |
| 데이터 의존 vs `.after()` | PVC 방식은 아티팩트 입출력이 없어 KFP가 순서를 추론하지 못하므로 `.after()` 필수 |
| `platforms.kubernetes` | 컴파일 YAML에서 `---` 뒤에 붙는 `pvcMount` 등 플랫폼 전용 스펙 |
| pvc-protection finalizer | 사용 중인 PVC의 삭제를 막는 K8s 보호 장치 |
| 경량 컴포넌트 직렬화 | 함수 본문만 YAML에 들어가므로 모듈 상수·외부 import를 참조하면 런타임 `NameError` |
| PVC 재사용 vs importer | 복사 없음·버전은 PVC 밖 vs 경로 계보 남음·단계별 업로드 비용 |
