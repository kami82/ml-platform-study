# CH4. 신뢰할 수 있는 ML 시스템 설계 (MLflow 실험 추적 + Feast 피처 스토어)

### 한 줄 요약

4장은 그림 1.4의 C(실험 추적)·B(모델 레지스트리)·D(피처 스토어)를 채우는 장이다. 소득 이진 분류기(≤50K / >50K)를 예제로, MLflow로 EDA 플롯·데이터셋·지표·모델·파라미터를 run 단위로 기록하고 최고 모델을 레지스트리에 등록한 뒤, Feast로 피처를 엔티티·FeatureView로 정의해 시점 기준(오프라인)과 최신값(온라인) 두 방식으로 조회한다.

<br>

### 주요 내용

**1. 2부와 4장의 위치**

-  실험과 수작업을 프로덕션 수준으로 바꾸는 도구가 MLflow(실험 추적·모델 레지스트리), Feast(피처 스토어), Kubeflow Pipelines(오케스트레이션), BentoML·Evidently(배포·드리프트 모니터링)다.
- 예제 데이터는 Adult 소득 데이터(30,162행). 고용형태·학력·혼인상태·직업·가구 내 관계·인종·성별·출신국가의 범주형 8열과 목표 변수 Target(≤50K / >50K)으로만 이루어져 있다. 코드는 https://github.com/practical-mlops/chapter-4.
- 흐름: EDA → 훈련/테스트 분할 → 의사결정 트리·랜덤 포레스트·XGBoost 훈련 → 최고 모델 등록 → Feast에 피처 등록·조회. 4장은 실험 추적과 피처 스토어까지, 배포는 5장(배치, KFP)과 6장(실시간, BentoML)으로 넘어간다.

**2. 왜 실험 추적이 필요한가 (4.1)**

- 추적 대상은 훈련/테스트 데이터, 모델 가중치, 정확도 지표 등. 이유는 **재현성**(동료와 결과 공유·복원), **모델 선택**(여러 모델 비교), **성능 추적**(재훈련 결과를 이전과 비교)이다.
- Git 커밋이나 파라미터 파일로도 가능하지만, 주기적 커밋·태그와 파일 사용법 설명이 부담이다. MLflow 추적 서버가 이 구조를 대신 잡아 준다.
- ML 엔지니어가 늘 받는 질문: 지금 프로덕션 모델은 어떤 버전인가, 어떤 파라미터가 최상이었나, 6개월 전 결과를 재현할 수 있나.

**3. EDA와 MLflow 추적 (4.1.1~4.1.2)**

- `describe`·`info`로 기술 통계를 보고, 범주형 8열 각각을 Target 비율 막대그래프로 그린다(plotnine, `position='fill'`로 건수 대신 비율, `coord_flip`으로 가로 막대). 예를 들어 자영업자는 >50K 비율이 높다.
- MLflow 개념 계층: **Experiment**(`income-classifier`) > **Run**(실행 1회, run ID) > Parameter / Metric / Artifact. EDA run은 `run_name=f"eda-{uuid}"`로 모델 run과 구분하고 `log_artifacts("categorical_variable_plots")`로 플롯 디렉터리를 올린다.
- 아티팩트는 MLflow 서버를 거치지 않고 **클라이언트가 S3(MinIO)에 직접 업로드**한다. 그래서 노트북에 AWS 키와 엔드포인트 환경 변수가 필요하고, 경로는 `s3://mlflow-artifacts/<실험ID>/<run ID>/artifacts/`다.
- 데이터 분할: Target은 OneHotEncoder로 0/1(>50K가 1, 약 24.9%), 범주형 8열은 `get_dummies(drop_first=True)`로 90개 숫자 열이 된다. 열 이름과 순서를 `column_list.pkl`로 저장해 두는 것이 핵심이다. 추론에서 같은 열 순서를 써야 하므로 5장의 추론 컴포넌트가 이 파일을 내려받는다. `train_test_split`은 80:20이고 `random_state`가 없어 실행마다 분할과 수치가 달라진다(실험 비교 시 고정과 `stratify` 권장).
- 리스팅 4.5(의사결정 트리): 훈련·테스트·참조(전체 feature_df) CSV를 MinIO `mlflow-datasets` 버킷에 올리고, `mlflow.data.from_pandas(df, source=…)` + `log_input(context="training"/"testing"/"reference")`로 기록한다. `log_input`은 열 정보와 행 수 같은 메타데이터만 남기고 데이터 자체는 MinIO에 있다. 이어 `fit` → `log_metric`(ROC AUC·정확도, 훈련/테스트) → `mlflow.sklearn.log_model` → `log_params`.
- XGBoost는 `mlflow.xgboost.autolog()` 한 줄로 파라미터·모델·피처 중요도 플롯이 자동 기록된다. 커스텀 지표는 직접 `log_metric` 해야 하고, 훈련 데이터는 데이터프레임이 아닌 배열로 기록된다.
- 실습 메모: 책 코드는 한 run 안에서 `xgb.train`을 두 번(logistic, hinge) 호출해 "Changing param values is not allowed" 경고가 나고 두 번째 파라미터·모델은 기록되지 않는다. 지표도 hinge의 0/1 출력으로 AUC를 계산해 0.72로 낮게 나온다. objective별로 run을 분리하면 logistic의 테스트 AUC가 0.86~0.87로 랜덤 포레스트와 비슷하거나 높다.
- **AUC**(ROC 곡선 아래 면적)는 무작위 양성·음성 쌍에서 모델이 양성에 더 높은 점수를 줄 확률이다. 이 데이터는 >50K가 25%라 전부 ≤50K라고 해도 정확도 75%가 나오므로, 세 모델의 정확도가 0.82 전후로 비슷해도 AUC(DT 0.82, RF 0.86, XGB-hinge 0.72)로 구분한다.
- 세 모델 비유: 의사결정 트리는 질문을 이어가는 스무고개 나무 한 그루(과적합 쉬움), 랜덤 포레스트는 조금씩 다른 나무를 많이 만들어 다수결, XGBoost는 앞 나무의 실수를 다음 나무가 보정하는 부스팅.

**4. MLflow 모델 레지스트리 (4.1.3)**

- UI 검색창에 `metrics.roc_auc_score_test > 0.8`을 넣고 차트 보기로 비교하거나, 클라이언트로 프로그래밍 방식으로 고른다: `get_experiment_by_name` → `search_runs(filter_string, order_by=["metrics.roc_auc_score_test DESC"], max_results=1)` → `runs:/<run_id>/income-classifier` → `register_model(model_uri, "random-forest-classifier")`.
- 등록된 모델은 Models 탭에서 버전과 원천 run을 볼 수 있고, 스테이징→프로덕션으로 승격할 수 있다. Prompts 탭은 아직 제한적이라 12~13장에서 Langfuse를 쓴다.
- 실습 메모(MLflow 3.0.0): `log_model`은 run 아티팩트 폴더가 아닌 별도 "logged model"로 저장된다. XGBoost autolog는 artifact path가 `model`이라 책의 `runs:/…/income-classifier` URI로는 찾지 못하므로, `mlflow.search_logged_models(filter_string="source_run_id = '…'")`로 model_id를 찾아 `models:/<model_id>`로 등록하는 편이 모델 종류와 무관하게 동작한다. AUC 1등이 XGBoost인데 "random-forest-classifier"로 등록하면 이름과 내용이 어긋나므로, 등록 이름에 모델 종류를 박지 않는 것이 안전하다.
- 5장과의 연결: 5장 추론 컴포넌트는 `current_stage == model_stage`인 버전을 찾고 그 run_id로 `column_list.pkl`을 받으며 `predict_proba`를 호출한다. 따라서 ① 등록 후 `transition_model_version_stage(name, version, "Production")`로 stage를 지정해야 하고(MLflow 3에서 deprecated지만 동작), ② `xgb.train`으로 만든 Booster는 `predict_proba`가 없어 sklearn 모델이어야 한다. 책이 랜덤 포레스트를 등록하는 이유다.
- 책은 테스트 점수로 모델을 고르지만, 운영에서는 검증셋으로 후보를 고르고 테스트셋은 마지막 확인에만 쓰는 편이 맞다. stage나 alias는 다른 버전을 가리킬 수 있으므로 배치 실행은 시작 시 `models:/이름/숫자`로 구체 버전을 고정해 기록한다.

**5. Feast 피처 스토어 (4.2)**

- 현실에서 피처는 여러 테이블·파일에 흩어져 있다. 이를 흉내 내려고 단일 CSV를 user_id·타임스탬프를 가진 세 parquet로 나눈다: **demographic**(Sex, Race, Native_country), **relationship**(Relationship, Marital-Status), **occupation**(Workclass, Education, Occupation).
- **시점 기준 조회(point-in-time)**: 5월 22일 기준으로 어떤 사용자의 피처를 가져올 때 1/7·5/21·12/4 기록 중 5/21 값을 써야 한다. 최신값을 가져오면 미래 정보가 섞인다. **TTL**은 얼마나 과거까지 볼지의 룩백 한계로, 2일이면 5/20 이전은 제외된다(책은 365일). 21일에 발생한 데이터가 23일에 도착했다면 22일에는 알 수 없었던 값이므로, 시간 필드 하나로 모든 누설이 막히지는 않는다.
- 설계(그림 4.10): 피처 파이프라인이 **오프라인 스토어**(MinIO parquet)를 채우고, **materialize**가 주기적으로 **온라인 스토어**(Redis)로 최신값을 옮긴다. **레지스트리**가 피처 정의와 스토어 정보를 보관하고, SDK가 양쪽 조회 메서드를 제공한다. 오프라인은 훈련·배치 추론, 온라인은 실시간 추론용이다.
- 정의 파일 세 개: `entity.py`의 `Entity(name="user_id")`, `features.py`의 `FileSource(ParquetFormat, path="s3://feature-data-sets/….parquet", s3_endpoint_override=MinIO 주소)`와 `FeatureView(name, entities=[user], schema=[Field…], ttl, source, tags)`, `feature_store.yaml`(project, `registry: s3://feature-registry/registry_local.db`, provider local, offline_store file, online_store redis + connection_string).
- `feast apply`는 **정의 등록**(Created entity / feature view, Deploying infrastructure), `feast materialize START END`는 **값 적재**다. 레지스트리에 FeatureView가 보여도 Redis는 비어 있다. 실습에서는 3개 뷰 × 30,162행을 적재했고 Redis 키는 30,162개(사용자당 해시 1개에 세 뷰의 필드가 함께 들어감).
- 조회: `get_historical_features(entity_df, features=["demographic:Sex"])`는 user_id·event_timestamp 열을 가진 데이터프레임을 받아 event_timestamp가 포함된 결과를 주고, `get_online_features(features, entity_rows=[{"user_id": …}])`는 시점 없이 Redis의 현재 값만 읽는다(MinIO는 읽지 않음). `None`이 나오면 materialize 여부와 해당 사용자의 원천 데이터를 확인한다.
- `feast serve`는 `POST /get-online-features` HTTP 엔드포인트를 띄워 SDK가 없는 언어에서도 쓰게 하고, `feast ui -p 8889`는 레지스트리의 엔티티·피처 뷰·데이터 소스·태그를 보여 준다.
- 주의: `feature_store.yaml`의 `localhost`는 PC 기준이다. Pod 안에서 localhost는 Pod 자신이므로 5장에서는 클러스터 주소를 쓰는 정의와 레지스트리(`registry.db`)를 따로 만든다.
- 책의 학습 노트북은 CSV를 직접 읽고 Feast는 뒤에서 별도로 준비한다. 즉 학습이 Feast에서 피처를 조회한 것은 아니며, 학습부터 추론까지 피처 계약이 고정된 것과는 다르다. 강화하려면 FeatureView들을 FeatureService로 묶어 학습이 그 서비스로 과거 피처를 조회하게 하고, MLflow run에 서비스 이름·피처 목록·정의 해시를 남긴다.

### 핵심 개념

| 개념 | 설명 |
| :--- | :--- |
| Experiment / Run | 관련 run을 묶는 단위 / 훈련·실험 1회 실행. run ID로 식별하고 파라미터·지표·아티팩트를 기록 |
| Parameter / Metric / Artifact | 실행 설정(트리 깊이 등) / 측정 결과(AUC, 정확도) / 실행이 남긴 파일(모델, 플롯, column_list.pkl) |
| log_input | 데이터셋의 메타데이터(열 정보, 행 수, 외부 경로)를 run에 기록. 데이터 자체를 복사하지는 않음 |
| autolog | 프레임워크 훈련 호출을 가로채 파라미터·모델·플롯을 자동 기록. 커스텀 지표는 직접 기록 |
| 모델 레지스트리 | 등록 모델의 이름·버전·stage(또는 alias)를 관리하는 저장소. 추론은 `models:/이름/버전`으로 로드 |
| ROC AUC | 양성·음성 쌍의 순서를 맞게 매길 확률. 불균형 데이터에서 정확도보다 신뢰할 만한 비교 지표 |
| column_list.pkl | 원-핫 인코딩 후 열 이름·순서 목록. 추론 입력을 같은 열로 `reindex`하기 위해 모델과 함께 보관 |
| Entity | 피처를 수집하는 대상의 식별자(조인 키). 예: user_id, product_id |
| FeatureView / FileSource | 피처의 논리적 묶음(이름, 엔티티, 스키마, TTL, 소스, 태그) / parquet 원천의 위치와 S3 엔드포인트 |
| Registry | 엔티티·FeatureView 정의와 스토어 설정의 메타데이터 파일(`registry_local.db`) |
| 오프라인 / 온라인 스토어 | 과거 이력(MinIO parquet, 훈련·배치용) / 최신값(Redis, 실시간용) |
| feast apply / materialize | 정의를 레지스트리에 등록 / 오프라인 값을 기간 지정으로 온라인에 적재 |
| 시점 기준 조회 / TTL | event_timestamp 이전의 가장 최근 값을 붙이는 조회 / 얼마나 과거까지 볼지 제한하는 룩백 윈도 |
| feast serve | 온라인 피처를 HTTP API로 제공하는 피처 서버 |

# CH5. ML 파이프라인 오케스트레이션 (Kubeflow Pipelines)

### 한 줄 요약

5장은 그림 1.4의 A(파이프라인 오케스트레이션)를 채우는 장이다. 4장의 모델과 피처로 "MinIO에서 대상 읽기 → Feast 피처 조회 → MLflow 모델 추론 → MinIO에 쓰기" 배치 추론을 Kubeflow Pipelines(KFP) v2 컴포넌트(컨테이너 + component.yaml)로 만들고, DAG 파이프라인으로 묶어 컴파일·업로드·실행한다.

<br>

### 주요 내용

**1. KFP가 하는 일 (5.1)**

- 대부분의 추론 파이프라인은 같은 구조다: 어딘가에서 데이터를 가져와 전처리하고, 모델을 로드해 추론하고, 결과를 DB나 스토리지에 쓴다. 주기 실행과 런타임 파라미터(날짜, 테이블 이름)도 필요하다. KFP는 이를 파이썬 SDK(`kfp`)로 정의하게 해 준다.
- 컴포넌트를 먼저 정의하고 조합해 파이프라인을 만든다. 각 컴포넌트는 자체 쿠버네티스 Pod에서 실행되므로 단계마다 격리된 환경이다.
- KFP는 단계의 순서와 의존성을 관리하고, 데이터는 Pod가 **파일로 저장해 다음 Pod에 전달**한다. 파이썬 객체나 메모리를 공유하는 구조가 아니다. 모델 이름·설정 같은 작은 값은 파라미터로, 대상 목록·피처 테이블은 파일 아티팩트로 넘긴다. `Input[Dataset]`/`Output[Dataset]`은 파일 전달 계약일 뿐 열 타입이나 결측 검사는 아니므로 스키마 검사는 컴포넌트 코드에서 한다.

**2. 컴포넌트 만드는 3단계 (5.1.1)**

- ① 컴포넌트가 할 일을 파이썬 파일로 작성(argparse `main`으로 인수 수신) → ② Dockerfile로 컨테이너화해 레지스트리에 푸시 → ③ `component.yaml`에 명세 작성(name, description, inputs/outputs와 타입, `implementation.container`의 image·command). 인수 값은 `{inputValue: x}`, 파일 입력은 `{inputPath: x}`, 파일 출력은 `{outputPath: x}`로 채운다.
- 디렉터리 구조는 `components/<이름>/component.yaml`과 `src/<이름>/<이름>.py`, 루트에 Dockerfile·requirements.txt. Dockerfile은 `COPY . /app`으로 저장소 전체를 넣으므로 네 컴포넌트 이미지는 내용이 같고 이름만 다르다(실습은 `book-ch5/components:0.1` 하나로 통일).

| 컴포넌트 | 입력 | 동작과 출력 |
| :--- | :--- | :--- |
| read_data | MinIO 접속 정보, 버킷, 파일명 | `fget_object`로 `entity_df.parquet`을 받아 DataFrame으로 읽고 `data_output_path`에 parquet 저장 |
| retrieve_features | MinIO의 `feature_store.yaml` 위치, entity_df(Dataset), feature_list(쉼표 문자열) | 설정 파일을 내려받아 FeatureStore 초기화 후 `get_historical_features`로 시점 기준 피처 조회 |
| run_inference | 피처(Dataset), model_name·model_type·model_stage, mlflow_host | `search_model_versions`에서 stage가 일치하는 버전의 run_id로 `column_list.pkl` 다운로드 → user_id·event_timestamp 제거 → `get_dummies` → `reindex(col_list)` → 프레임워크별 `load_model("models:/이름/stage")` → `predict_proba[:,1]`을 `Predicted_Income_Class` 열로 추가 |
| write_data | 예측 결과(Artifact), 출력 버킷·파일명 | parquet으로 저장해 `fput_object`로 MinIO에 업로드 |

- 설계 원칙: **모듈성**(단일 책임, 추론과 쓰기 분리), **입출력 명시**, **파라미터화**(mlflow_host·bucket_name을 하드코딩하지 않음), **문서화**. 이점은 **재사용**, **협업**(팀원이 컴포넌트를 나눠 병렬 개발), **개별 테스트**(문제를 컴포넌트로 격리).
- 실습 메모: `run_inference`의 `get_dummies(drop_first=True)`는 배치에 없는 범주가 있으면 기준 열이 달라져 조용히 틀린 예측이 나올 수 있다. 전체 30,162행을 넣는 이번 실습은 모든 범주가 있어 괜찮다. access_key·secret_key가 파이프라인 파라미터라 실행 이력에 평문으로 남는 것도 주의.

**3. 클러스터 안에서 Feast 레지스트리 다시 만들기**

- 4장의 `registry_local.db`는 데이터 소스의 `s3_endpoint_override`가 localhost라 Pod에서 쓸 수 없다. `minio-service.kubeflow.svc.cluster.local:9000`을 가리키는 `features.py`와 `s3://feature-registry/registry.db`를 쓰는 `feature_store.yaml`로 **쿠버네티스 Job**(`feast apply`)을 클러스터 안에서 실행한다. Job은 Deployment와 비슷하지만 명령이 끝나면 종료된다.
- 호스트에서 같은 정의로 `feast apply`를 하면 서비스 이름을 해석하지 못해 실패한다. 이미지를 빌드하지 않으려면 공식 python 이미지 + ConfigMap으로 정의 파일을 마운트해 Job에서 pip 설치 후 실행하는 방법도 된다.
- 클러스터용 `feature_store.yaml`도 `feature-registry` 버킷에 따로 올린다(실습은 `feature_store_k8s.yaml`). `ErrImageNeverPull`이면 kind에 이미지 적재부터 확인하고, 재실행은 Job을 지우고 다시 apply한다.

**4. 파이프라인 정의·컴파일·실행 (5.1.2)**

- 파이프라인은 컴포넌트의 **DAG**(방향 있고 순환 없는 그래프)다. `kfp.components.load_component_from_file`로 네 컴포넌트 객체를 만들고, `@dsl.pipeline` 함수의 인수(14개, 모두 str, 기본값 없음)가 런타임 파라미터가 된다.
- 연결은 `retrieve_features_op(entity_df=fetch_data_task.outputs["data_output"], …)`처럼 **앞 작업의 outputs를 입력으로 넘기면** 의존성이 자동으로 생긴다. `compiler.Compiler().compile(func, "income_classifier_pipeline.yaml")`로 IR YAML을 만든다. 컴파일은 명세 변환일 뿐 Pod를 만들거나 데이터를 읽지 않으므로 이미지·주소·권한 문제는 실행에서 드러난다.
- IR YAML 구조: `components`(각 컴포넌트의 input/outputDefinitions, 아티팩트 타입 `system.Dataset`), `deploymentSpec.executors`(image와 command, `{{$.inputs.parameters['x']}}`·`{{$.inputs.artifacts['x'].path}}` 치환), `root.dag.tasks`(`dependentTasks`, `taskOutputArtifact`로 producerTask 지정), `root.inputDefinitions`.
- UI 흐름: **Pipelines → Upload pipeline**(YAML 선택) → 그래프 확인 → **Experiments → Create experiment** → **Create run**에서 파이프라인 선택, 파라미터 입력 → **Start**. KFP 실험은 파이프라인 실행을 묶고 MLflow 실험은 학습 run을 묶는다. 이름이 같아도 별개다.
- 실행 파라미터(값 예): minio_host `minio-service.kubeflow.svc.cluster.local:9000`, entity_df `feature-data-sets/entity_df.parquet`, feature store `feature-registry/feature_store_k8s.yaml`, feature_list `demographic:Sex,demographic:Race,demographic:Native_country,relationship:Relationship,relationship:Marital-Status,occupation:Workclass,occupation:Education,occupation:Occupation`, model `random-forest-classifier`/`sklearn`/`Production`, mlflow_host `http://mlflow-service.mlflow.svc.cluster.local:5000`, output `inference-datasets/income_predictions.parquet`. Pod 안에서 localhost는 자기 자신이므로 MLflow 주소는 서비스 이름이나 노드 IP여야 한다.
- 실행하면 뒤에서 **Argo Workflows** CRD(`workflows.argoproj.io`)가 만들어지고, 작업마다 `system-dag-driver`, `system-container-driver`, `system-container-impl` Pod가 뜬다. 네 작업이 차례로 완료되기까지 약 2~4분. 결과는 30,162행 × 91열(마지막이 `Predicted_Income_Class`), 고소득 예측 약 22%로 모델을 직접 로드해 계산한 값과 일치했다.
- **Argo CD vs Argo Workflows**: Argo CD는 책이 Kubeflow 설치에 고른 GitOps 도구이고, Argo Workflows는 KFP가 파이프라인 작업을 Pod로 실행하는 엔진이다. Kubeflow를 설치한다고 Argo CD가 생기는 것은 아니다.
- 자주 막히는 지점: `No model found in stage Production`은 model_name·stage 오타(대소문자 구분) 또는 stage 미지정, Pod가 Init에서 멈추면 사용자 네임스페이스의 `mlpipeline-minio-artifact` Secret 누락, 모델 run에 `column_list.pkl`이 없으면 다운로드 실패.

**5. KFP standalone 설치 (스터디 공유)**

- Kubeflow 전체(대시보드·노트북·KServe·인증)는 노트북에 무겁다. 파이프라인만 쓰려면 `cluster-scoped-resources`(CRD) 적용 → `crd/applications.app.k8s.io` established 대기 → `env/platform-agnostic` 적용 순으로 KFP standalone을 설치하고, `ml-pipeline-ui`를 NodePort로 바꿔 접속한다.
- UI 업로드 대신 `kfp.Client(host).create_run_from_pipeline_package(yaml, arguments)`로 바로 실행할 수 있다. `@dsl.component(base_image=…)`로 파이썬 함수를 경량 컴포넌트로 만들어 `first.output`을 다음 단계 입력으로 넘기는 예제로 단계 간 값 전달을 확인했다.
- Apple Silicon에서는 일부 KFP 이미지가 amd64 전용이라 Docker Desktop의 Rosetta 에뮬레이션을 켜야 한다. Pod가 `exec format error`로 죽으면 이 설정부터 본다.

### 핵심 개념

| 개념 | 설명 |
| :--- | :--- |
| 오케스트레이션 | 여러 파이프라인을 실행하며 각 단계에 데이터와 컴퓨팅 자원이 갖춰지도록 순서·의존성을 관리하는 일 |
| 컴포넌트 | ML 워크플로 안의 재사용·조합 가능한 작업 단위. 파이썬 코드 + 컨테이너 이미지 + component.yaml |
| component.yaml | 컴포넌트의 이름·입출력 타입·이미지·실행 명령 명세. `inputValue`/`inputPath`/`outputPath`로 인수를 채움 |
| Dataset / Artifact 타입 | 컴포넌트 사이에 파일로 전달되는 입출력. 경로 전달 계약이지 스키마 검증은 아님 |
| 파이프라인 / DAG | `@dsl.pipeline` 함수로 정의한 컴포넌트 그래프. 출력→입력 연결이 의존성이 됨 |
| 컴파일 / IR YAML | 파이프라인 함수를 KFP가 읽는 실행 명세로 변환. Pod 생성이나 데이터 읽기는 하지 않음 |
| KFP 실험 / 실행(run) | 파이프라인 실행을 묶는 단위 / 파이프라인이 실제로 실행된 인스턴스 |
| Argo Workflows | KFP가 각 작업을 Pod로 실행하는 엔진. `workflows.argoproj.io` CRD로 상태 확인 |
| 쿠버네티스 Job | 명령이 끝나면 종료되는 워크로드. 클러스터 안에서 `feast apply`를 실행하는 데 사용 |
| model_stage | 레지스트리에서 추론용 버전을 고르는 기준(Production 등). 실행 시 구체 버전 고정이 더 안전 |
| 멀티 아키텍처 이미지 | `docker buildx --platform linux/amd64,linux/arm64`로 한 태그에 두 아키텍처를 담는 빌드 |
