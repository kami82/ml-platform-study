# CH6. ML 모델 프로덕션화 (BentoML 서빙 + Evidently 드리프트 모니터링)

### 한 줄 요약

6장은 그림 1.4의 E(모델을 API로 배포)와 그 뒤의 모니터링을 채우는 장이다. 4·5장의 소득 분류기를 BentoML로 Bento(모델 + 서빙 코드 + 환경)로 패키징해 Yatai로 쿠버네티스에 실시간 API로 배포하고, Evidently로 참조 데이터와 현재 데이터의 분포 차이를 통계 검정해 배치(KFP 컴포넌트)와 실시간(마이크로배치) 양쪽에서 데이터 드리프트 대시보드를 채운다.

<br>

### 주요 내용

**1. 6장의 위치와 흐름**

- 5장이 배치 파이프라인 배포였다면 6장은 **배포(실시간 API)** 와 **모니터링(데이터 드리프트)** 두 과제를 다룬다. 전통 ML과 LLM 모두에 적용되는 내용이고, LLM 전용(프롬프트·관측·평가)은 12장에서 다룬다.
- 3장 hello-joker는 Dockerfile, K8s 매니페스트, 모니터링 로직을 직접 썼다. 데이터 과학자 모두가 이를 다룰 수 없으므로 BentoML이 `bentofile.yaml` 하나로 이 과정을 표준화한다.
- 역할 분담: **MLflow** = 실험 기록과 "어떤 버전이 승인됐나"의 기준, **Bento** = 승인된 모델을 코드와 함께 고정한 배포 단위(tar 묶음, 컨테이너는 아님), **Yatai** = Bento를 이미지로 만들어 배포·관리하는 도구.
- 코드: https://github.com/practical-mlops/chapter-6 (BentoML 1.1.10, Python 3.10, Evidently 0.5.0).

**2. BentoML 배포 플랫폼 (6.1)**

- 흐름: 로컬에서 Bento 빌드 → Yatai에 푸시 → Yatai가 컨테이너화·배포(그림 6.2). Yatai 스택은 세 컴포넌트다.

| 컴포넌트 | 역할 |
| :--- | :--- |
| yatai | 모델·Bento를 오브젝트 스토리지에 저장하는 레지스트리 + 대시보드 UI |
| yatai-image-builder | Bento를 컨테이너 이미지로 빌드(kaniko Job)해 레지스트리에 푸시 |
| yatai-deployment | 빌드된 이미지를 BentoDeployment CR로 배포(API 서버 + 러너 파드, HPA, Ingress) |

- BentoML(오픈소스 프레임워크, 인프라는 직접 준비, 6장은 Yatai로 K8s 운영)과 BentoCloud(관리형 플랫폼, 빌드·배포·스케일링 대행)는 대체 관계가 아니라 같은 Bento를 다른 방식으로 운영하는 관계다. `service.py`는 그대로 쓰는 것이 설계 의도.
- **Bento 빌드 4단계 (6.1.1)**
  1. 모델 등록: `bentoml.mlflow.import_model(name, model_uri="models:/<이름>/Production")`으로 MLflow 모델을 로컬 Bento 스토어로 옮긴다. `bentoml models list`의 Module 열이 출처(`bentoml.mlflow`)를 보여 준다.
  2. 서비스·러너 초기화: **러너**는 원격 파이썬 워커에서 실행되는 독립 확장 가능한 연산 단위다. `bentoml.mlflow.get(name).to_runner()`로 MLflow 모델을 러너로 바꾸고 `bentoml.Service`에 묶는다. `initialize` 함수에서 Feast 피처 스토어 설정과 더미 변수용 열 목록(MLflow 아티팩트)을 읽는다.
  3. 서비스 정의: 입력은 `user_id`(Feast 엔티티)를 담은 JSON. `/predict`는 Feast 온라인 스토어(Redis)에서 피처를 읽어 더미 변수로 바꾼 뒤 러너로 예측해 `{"income_category": ...}`를 돌려준다.
  4. `bentofile.yaml`: Dockerfile보다 간결한 패키징 명세. `service: "service:svc"`(파일명:객체명), `labels`(담당자 등 메타데이터), `include`(포함 파일), `python.requirements_txt`, `docker.env`(설정 파일을 고르는 `ENV_NAME`, Feast가 MinIO를 읽을 AWS 키).
- **빌드·푸시 (6.1.2)**: `bentoml build -f bento/bentofile.yaml` → `bentoml list`(Size는 앱, Model Size는 모델 크기) → `bentoml containerize` → `docker run -p 3000:3000`(MinIO·Redis·MLflow 포트 포워딩 필요) → `bentoml yatai login --api-token … --endpoint …` → `bentoml push`(모델과 Bento가 함께 올라감).
- **배포 (6.1.3)**: Yatai UI Models·Bentos 탭에서 푸시 확인 → Deployments > Create에서 클러스터(default), 네임스페이스(yatai), Bento 태그, 복제본 수, CPU·메모리(API 서버와 러너 각각) 지정 → Yatai가 `yatai-bento-image-builder-…` Job으로 이미지 빌드 → **API 서버 파드**(프런트엔드)와 **러너 파드**(추론)가 뜨고 둘은 독립적으로 스케일된다 → Ingress 자동 생성 → 루트에서 Swagger UI로 `/predict` 테스트. `/metrics`도 기본 제공되어 Prometheus가 초당 요청 수·지연 시간을 긁어갈 수 있다.

**3. Evidently 데이터 드리프트 모니터링 (6.2)**

- 데이터 드리프트: 훈련 데이터의 통계적 특성이 변해 모델 성능이 시간이 갈수록 떨어지는 현상. 모델은 입력·출력의 관계와 입력 분포가 유지된다고 가정하지만 현실 데이터는 그렇지 않다.

| 드리프트 유형 | 설명 |
| :--- | :--- |
| 레이블 드리프트 | 목표 변수의 정의 자체가 바뀜(예: '불량'의 기준 변경) |
| 사전 확률 이동 | 클래스 비율이 바뀜(예: 사기 거래 비율 변화) |
| 공변량 이동 | 입력 피처의 분포가 바뀜(인구통계·위치·행동 양식 변화) |
| 급격한 드리프트 | 팬데믹·시장 사건 등 외부 요인으로 갑자기 바뀜 |

- 통계 검정: **KS 검정**(수치형, 두 CDF 비교, p-value < 0.05면 드리프트), **카이제곱 검정**(범주형, 범주 분포 변화), **바서슈타인 거리**(수치형, 기준 분포와의 거리, 클수록 드리프트). Evidently가 데이터에 맞는 검정을 자동 선택하고 직접 지정도 가능하다.
- **보고서와 대시보드 (6.2.1)**
  - **Report**는 검사 항목(**Metric**)을 담는 바구니. 단일형(`DatasetMissingValuesMetric`)과 묶음형(`DatasetSummaryMetric`), 데이터셋 수준과 컬럼 수준이 있다. **프리셋**은 용도별 종합검진 패키지(`DataDriftPreset`, `DataQualityPreset`, `RegressionPreset`).
  - 최소 코드: `Report(metrics=[DataDriftPreset()])` → `report.run(reference_data=, current_data=)` → `save_html()`.
  - **두 단계 판정**: 컬럼마다 드리프트 판정(바서슈타인은 0.1 초과, p-value 검정은 0.05 미만) → 드리프트 컬럼 비율이 데이터셋 임곗값 0.5를 넘으면 데이터셋 드리프트. 그림 6.16은 8열 중 6열(0.75)이라 detected. 컬럼 임곗값 0.1과 데이터셋 임곗값 0.5는 다른 값이다.
  - 시간에 따라 추적하려면 스냅샷을 여러 번 쌓아야 하므로 `evidently ui`(대시보드 서버)를 쓴다. **워크스페이스**는 스냅샷을 보관하는 디렉터리, **프로젝트**는 그 하위 디렉터리. `RemoteWorkspace(url).create_project(name=…)`로 만든다.
  - **패널**은 보고서 지표를 대시보드에 그린 시각화 요소. 제목 패널은 `DashboardPanelCounter(filter=ReportFilter(…), agg=CounterAgg.NONE, title=…)`, 값 패널은 `value=PanelValue(metric_id="DatasetDriftMetric", field_path="share_of_drifted_columns", legend=…)`에 `agg=LAST`(가장 최근 스냅샷). `project.dashboard.add_panel()` 뒤 `project.save()`를 꼭 호출해야 UI에 반영된다.
- **배치: KFP 컴포넌트 (6.2.2)**: `detect_drift.py`는 MLflow에서 `model_stage`에 해당하는 모델 버전의 run ID를 찾고, `run.inputs.dataset_inputs`의 태그에서 참조 데이터셋(4.1.2에서 `log_input`으로 기록)의 MinIO 경로를 얻어 내려받은 뒤, 현재 피처와 비교한 Report를 Evidently 프로젝트에 추가한다. 5장 추론 파이프라인에 끼워 넣으면 `fetch_data → retrieve_features → detect_drift → run_inference → write_data`가 된다. 실행마다 대시보드가 갱신된다.
- **실시간: API 드리프트 (6.2.3)**: 요청 1건은 분포가 아니므로 검정할 수 없다. 최근 N건(윈도)을 모은 **마이크로배치**를 참조 데이터와 비교한다. `MonitoringService`는 `iterate(new_rows)`로 새 행을 윈도에 붙이고, 윈도 크기를 넘으면 Report를 실행해 `workspace.add_report()`하고 오래된 행을 버린다(컨베이어 벨트 비유). `initialize`에서 참조 데이터셋·RemoteWorkspace·프로젝트 ID(.env)를 준비하고 `predict`에서 `ctx.state["monitoring_service"].iterate(feature_df)`를 호출한다. `bentofile_with_drift.yaml`로 빌드하고 `generate_mock_request.py`로 수백 건을 보내 확인한다.
  - 윈도 50에서 드리프트 피처 비율이 0.875까지 나오는 것은 모델이 변한 게 아니라 표본이 작아 검정이 불안정하기 때문이다. 대응: 윈도를 키우기(200, 500), 임곗값 올리기, 연속 N회 초과 시에만 알림.
- 드리프트를 만났을 때: ① 유형·심각도 조사 → ② 업스트림 파이프라인·전처리 수정 → ③ 최신 데이터로 재훈련 → ④ 피처 선택 갱신. 모니터링은 일회성 절차가 아니라 지속적인 운영이다.

**4. 책 vs 스터디 실습 환경**

| 구성 요소 | 책 | 스터디 실습 |
| :--- | :--- | :--- |
| 실습 기반 | 부록 A 환경 | 4·5장 kind 환경(KFP standalone 2.4.1, MLflow 3.0.0, MinIO, Redis) 위에 추가. 리모트 서버에서 실행하고 포트는 127.0.0.1만 열어 SSH 터널로 접속 |
| 저자 코드 | mlflow 2.7.0, buster 이미지 | mlflow 3.0.0으로 서버와 맞춤, bentoml 주석 해제, `litestar==2.12.1`·`sniffio` 추가(multipart 충돌), `slim-buster`→`slim-bookworm`, 컴포넌트 이미지를 로컬 빌드 이미지로 |
| 컨테이너화 | `bentoml containerize` | 이 환경에서 NotImplementedError. `bentoml._internal.container.build(tag, backend="docker")`를 파이썬으로 직접 호출. Bento 디렉터리에서 `docker build`를 돌리면 모델이 빠진 이미지가 됨 |
| 로컬 실행 | `docker run -p 3000:3000` | 포워딩이 127.0.0.1에만 열려 `--network host --add-host host.docker.internal:127.0.0.1` |
| Yatai | Helm 설치(A.6) | 1.1.13(마지막 릴리스)을 ClusterIP로. PostgreSQL에 yatai DB·롤, MinIO `yatai` 버킷, 비밀번호는 Secret. 차트 이름은 `bentoml/yatai`. values 기본 키에 오타가 있어 `s3.accessKeyExistingSecretKey`를 직접 지정. 초기화 토큰으로 `/setup` 후 API 토큰 발급 |
| 배포 스택 | Yatai UI | cert-manager + 클러스터 내부 Docker 레지스트리(노드 프록시 포함) + yatai-image-builder + yatai-deployment 1.1.13. ingress-nginx 미설치, 접속은 port-forward |
| Evidently UI | 로컬 `evidently ui` | `ENTRYPOINT ["evidently","ui"]` 이미지를 빌드해 `kind load`, PVC + Deployment + ClusterIP로 배포 |
| KFP 제출 | UI | `kfp.Client().upload_pipeline()` + `create_run_from_pipeline_package()`를 heredoc 스크립트로 실행하고 `get_run().state` 폴링 |

- **실습 메모**
  - 빌더 파드(kaniko)가 OOMKilled → `BentoRequest`의 `imageBuilderContainerResources`를 patch로 상향(limit 6Gi). 배포 결과는 API 서버 파드(main + envoy proxy + metrics-transformer), 러너 파드, HPA, Ingress(구현체가 없어 port-forward로 접속).
  - 배포된 Bento가 `production.env`의 MLflow·Feast·Redis 주소로 localhost 포워딩을 바라보면 파드 안에서 닿지 않아 500이 난다. 클러스터 내부 주소로 바꿔야 한다. 같은 이유로 KFP 파이프라인의 `evidently_workspace_url`도 `http://evidently-ui.evidently.svc.cluster.local:8000` 같은 내부 DNS를 쓴다.
  - Evidently 프로젝트·패널 생성 스크립트는 1회만 실행하고, 출력된 프로젝트 ID(저자 UUID와 다름)를 `.env`와 `production.env`의 `EVIDENTLY_PROJECT_ID`에 넣는다.
  - 드리프트 파이프라인 재실행 시 `enable_caching=False`가 필요하다. 코드는 `fetch_data`만 캐싱을 꺼 두어서, 입력이 같으면 나머지 단계가 캐시 적중으로 건너뛰어 리포트가 쌓이지 않는다. UI의 Clone run으로도 재실행 가능.
  - `run_inference`는 `.after(detect_drift_task)`라 순서만 보장한다. 드리프트가 탐지돼도 추론은 진행되며, 중단·분기하려면 드리프트 여부를 출력으로 받아 `dsl.If`로 묶어야 한다.
  - 드리프트 BentoML 서비스는 `BENTOML_CONFIG_OPTIONS="api_server.workers=1"`이 필수다. 워커가 여럿이면 같은 디렉터리에 동시에 쓰다 시작 오류가 나고, 윈도(100행)가 워커별로 나뉘어 리포트가 생기지 않는다. `mock_request_data.csv` 100건을 보내면 로그에 "Running report"가 찍힌다.
  - 모임장 2026 최신화 핸즈온(https://github.com/choisungwook/portfolio 의 ml-platform-engineering-part2)은 BentoML·Yatai 대신 **KServe v0.19.0**(Standard 모드, `mlflow-serve` 런타임)으로 MLflow 레지스트리의 champion 모델을 `InferenceService` 하나로 Deployment·Service·외부 경로까지 만든다. 모델 레지스트리는 stage 대신 alias(`models:/<이름>@champion`)를 써서 pull 코드 수정 없이 새 버전으로 교체된다. 책 부록 A(Kubeflow 1.7 전체, MinIO, Yatai, 로컬 Jupyter)를 Kubeflow 26.03.1 선별 16개 컴포넌트, SeaweedFS, KServe, Kubeflow Notebooks로 바꾼 구성이며 Argo CD ApplicationSet으로 배포한다.
- 도전과제: Yatai 배포를 UI 대신 K8s CRD(`BentoRequest`, `BentoDeployment`)로 / 내부 레지스트리 대신 DockerHub·Harbor / Yatai 레지스트리 대체(KitOps 등 OCI 아티팩트) / yatai-image-builder 대체(KFP로 빌드·배포 자동화) / yatai-deployment 대체(KServe로 MLflow 모델 서빙) / `/metrics`를 Prometheus로 수집해 Grafana 대시보드 만들기.

### 핵심 개념

| 개념 | 설명 |
| :--- | :--- |
| Bento | 모델·서빙 코드·의존성·환경 변수를 묶은 BentoML의 배포 단위. 도커 이미지와 비슷하지만 tar 묶음이고 컨테이너화는 별도 단계 |
| 서비스 / 러너 | 서빙 로직(피처 조회 → 추론)을 정의하는 `bentoml.Service` / 추론을 수행하며 워커 단위로 독립 확장되는 연산 단위 |

# CH7. 데이터 분석 및 준비 (Kubeflow Notebooks + KFP 데이터 전달)

### 한 줄 요약

7장은 3부 캡스톤 프로젝트(신분증 객체 탐지, MovieLens 영화 추천)의 첫 단계인 데이터 분석과 준비를 다룬다. Kubeflow Notebooks로 데이터와 가까운 곳에 분석 환경을 띄우는 방법(이미지, 볼륨, PodDefault, 메뉴·이미지 커스터마이징)을 익히고, KFP v2 컴포넌트 사이에서 작은 값은 반환값으로, 큰 데이터는 아티팩트 경로로 넘기는 원리를 농담 생성 파이프라인으로 확인한 뒤 캡스톤 데이터 준비 파이프라인으로 이어진다. 스터디 3주차는 7.1~7.2.1까지이며 7.2.2~7.3은 4주차에 진행한다.

<br>

### 주요 내용

**1. 3부와 7장의 위치**

- 3부는 원칙·인프라·플랫폼 구성 요소를 실제 프로젝트에 적용하는 부분이다. 캡스톤 1은 **신분증 탐지**(YOLO 변형으로 객체 탐지 파이프라인 구축, 성패가 데이터 준비에 달려 있음을 확인), 캡스톤 2는 **MovieLens 영화 추천**(날짜형 데이터 처리 개념, 컴포넌트 6개로 데이터 준비 파이프라인 구성).
- 7장 범위: 큐브플로 노트북 이미지 빌드·실행, 노트북으로 데이터 분석, 파이프라인에서 데이터 전달, 데이터를 전달하는 컴포넌트 작성, 객체 탐지 데이터 준비 파이프라인.
- 새 아키텍처가 매주 나오지만 성공은 가장 화려하지 않은 데이터 준비에 달려 있다. "쓰레기를 넣으면 쓰레기가 나온다"는 입력 데이터 품질이 모델 결과의 신뢰성을 결정한다는 뜻이다.
- 캡스톤 전에 간단한 농담 생성 파이프라인으로 노트북 분석, 데이터 전달 개념을 복습한다. 코드: 7.2·7.3.1은 장 저장소, 7.3.2는 https://github.com/practical-mlops/movie-recommender-project

**2. Kubeflow Notebooks (7.1)**

- 데이터 분석의 제약: 아무리 큰 데이터셋이라도 데이터에 가까운 곳에서 실행해야 하고, GPU 같은 비싼 자원에 대화식으로 접근해야 하며, 배포 환경을 최대한 닮은 환경에서 버전 관리·CI/CD를 적용해야 한다. 큐브플로 노트북은 이를 해결하면서 Jupyter, VS Code(code-server), RStudio를 브라우저로 제공하고 파이프라인과 같은 베이스 이미지를 쓸 수 있다.
- **7.1.1 서버 실행**: UI Notebooks > NEW NOTEBOOK. 네임스페이스 선택이 리소스 할당량·볼륨·시크릿에 영향을 준다. 이미지(샘플 또는 커스텀), 리소스(K8s limits/requests와 동일, 테스트라도 메모리를 너무 낮게 잡지 말 것), GPU·TPU 수량(오버프로비저닝이 없으면 다른 파드가 못 씀).
- **7.1.2 볼륨**: 워크스페이스 볼륨은 `/home/jovyan`에 자동 마운트되는 영구 저장소(기본 스토리지 클래스로 생성). 데이터 볼륨은 기존 PVC를 런타임에 추가 마운트. PVC는 컨테이너가 스토리지를 요청하는 수단이다.
- **7.1.3 설정·어피니티·톨러레이션**: **설정(Configurations)** 은 네임스페이스의 `PodDefault`(`kubeflow.org/v1alpha1`)를 가리킨다. `selector.matchLabels`에 맞는 파드에 `env`(예: `MLFLOW_TRACKING_URI`)나 볼륨을 런타임에 주입한다. 어피니티는 파드를 특정 노드로 유인하고 톨러레이션은 테인트된 노드에 배치를 허용한다. 공유 메모리는 분산 훈련·메모리 캐시 데이터 로더에 유리. 생성된 노트북은 `notebooks.kubeflow.org` CRD로 조회된다.
- **7.1.4 메뉴 커스터마이징**: `jupyter-web-app-config` ConfigMap의 `spawnerFormDefaults`를 편집한다. 각 옵션에 기본값과 `readOnly`가 있고 readOnly면 사용자가 못 바꾼다. `image`(Jupyter)·`imageGroupOne`(code-server)·`imageGroupTwo`(RStudio)의 `value`가 기본, `options`가 선택지. `affinityConfig.options`로 small-cpu/large-cpu 셀렉터를 제시하면 기본은 소형 노드, 고성능 노드는 필요한 노트북만 쓰게 할 수 있다.
- **7.1.5 커스텀 이미지**: 계층은 베이스 이미지 → code-server/Jupyter 런타임 의존성 → 런타임 → 큐브플로 호환용 노트북 서버 실행 설정 파일. 프로젝트 저장소의 멀티스테이지 Dockerfile이 베이스 이미지를 인수로 받아 둘 중 하나를 빌드한다.
- 동작 원리: `Notebook` CR을 notebook-controller가 감지해 StatefulSet, Service, (Istio 사용 시) VirtualService를 만든다.

**3. KFP 데이터 전달 (7.2)**

- 컴포넌트는 각각 별도 파드(격리 환경)에서 실행되므로 데이터를 주고받는 메커니즘이 필요하다. **작은 값**은 반환값(`-> str/int`)과 `.output`으로, **큰 데이터**는 `Output[Artifact/Dataset]`의 `.path`(파일·디렉터리 경로)로 넘긴다.
- **7.2.1 단순 값 전달**: `generate_joke`(pyjokes) → `count_words` → `output_result` 세 함수를 `@dsl.component`로 바꾸고 `@dsl.pipeline`에서 `.output`으로 연결한다.
  - **import는 반드시 함수 안에** 쓴다. 의존성이 함수에 캡슐화되어 컨테이너로 패키징하기 쉽다.
  - 패키지 관리 규칙 3가지: `base_image`에 이미 설치 / `packages_to_install`에 명시(requirements.txt와 유사) / 함수 안에서 subprocess로 pip install(명시성이 떨어져 비권장).
  - 컴파일된 YAML의 세 부분: `components`(타입이 지정된 입출력 인터페이스), `deploymentSpec.executors`(container의 image·args·command), `root.dag.tasks`(연결과 캐싱). command는 ① pip 확인 후 kfp 설치 → ② 임시 디렉터리에 `ephemeral_component.py`로 함수 코드를 쓰고 `kfp.dsl.executor_main`으로 실행. 즉 KFP는 **코드 인젝션** 방식으로 직렬화·전달 헬퍼를 함수 둘레에 붙인다.
- **값 vs 경로 실험 결과 (스터디, kfp 2.9.0 + 백엔드 2.4.1)**

| 실험 | 결과 | 원인·관찰 |
| :--- | :--- | :--- |
| 값 전달 10KB, 60KB | 성공 | - |
| 값 전달 100KB | 실패 | argument list too long. 값이 파드 명령 인자에 들어감 |
| 값 전달 1MB | 실패 | annotations 262144바이트 초과로 다음 파드 미생성 |
| 값 전달 10MB | 실패 | MLMD gRPC 4MB 한도 |
| 경로 전달 10MB, 200MB | 성공 | 디렉터리 아티팩트는 MinIO 키 접두사로 저장 |
| 책 코드 그대로 `np.save` | 실패 | `.npy` 확장자가 자동으로 붙어 FileNotFoundError. 파일 핸들로 쓰면 성공 |
| 아티팩트 타입 7종 | 성공 | MLMD에 `system.*` 타입 등록 |

  - 아티팩트 로컬 경로는 `/minio/mlpipeline/v2/artifacts/<파이프라인>/<run_id>/<태스크>/<실행UUID>/<이름>`이며 실제 저장소는 MinIO `mlpipeline` 버킷의 같은 키다. `Metrics`·`ClassificationMetrics`는 파일 없이 MLMD(MySQL `metadb`)에만 저장된다.
- **7.2.2 경로 전달, 7.2.3 아티팩트 타입, 7.3 데이터 준비 실전**(객체 탐지 download → split, 영화 추천 컴포넌트 6개 + QA)은 4주차에 진행.

**4. 책 vs 스터디 실습 환경**

| 구성 요소 | 책 | 스터디 실습 |
| :--- | :--- | :--- |
| Kubeflow | 전체 배포판(Central Dashboard, Jupyter Web App, Istio, Profile) | kind에는 KFP standalone만 있어 **notebook-controller + PodDefault 웹훅만 설치**하고 `Notebook`·`PodDefault` CR을 직접 작성(경량 대체). 7.1.4 메뉴 커스터마이징은 Web App이 없어 해당 없음 |
| 매니페스트 출처 | - | Kubeflow 배포판 26.03.1을 kustomize로 렌더링. PodDefault 웹훅은 dashboard 하위(notebooks 아님), 이미지 `poddefaults-webhook:v2.0.0`, notebook-controller v1.11.0 |
| 네임스페이스 | Profile 컨트롤러가 생성·라벨링 | 웹훅의 namespaceSelector가 `app.kubernetes.io/part-of=kubeflow-profile` 라벨을 요구하므로 네임스페이스에 직접 붙여야 주입된다 |
| 접속 | Dashboard 경유 | Istio 없이 `USE_ISTIO=false`. Service port-forward + SSH 터널. URL에 `NB_PREFIX`(`/notebook/<ns>/<name>/`) 접두사가 없으면 404 |
| 노트북 이미지 | jupyter-scipy v1.6.1 | `jupyter-scipy:v1.11.0`. mlflow·boto3는 없어 pip 설치(워크스페이스에 남음) |
| PodDefault | 프록시 변수 예제(리스트 7.1) | `add-ml-env`로 `MLFLOW_TRACKING_URI`, `KF_PIPELINES_ENDPOINT` 주입. 노트북에서 `kfp.Client()`를 인자 없이 호출하면 주입된 엔드포인트로 접속 |
| 데이터 전달 실습 | 리스트 7.4~7.8 | `a1`(값)·`a2`(경로)·`a2b`(크기 비교)·`a3`(v1→v2)·`a4`(타입 7종) 스크립트 + `submit.py`(제출·대기·로그 출력)·`inspect_yaml.py`(코드 인젝션 확인)·`list_minio.py`/`show_artifacts.py` |

- **실습 메모**
  - `Notebook` CR의 `metadata.labels`가 파드에 그대로 전파되고 PodDefault의 `selector.matchLabels`와 맞으면 env·볼륨이 주입된다. PodDefault를 바꾸면 파드를 다시 만들어야 한다.
  - 노트북 파드는 최대 4Gi를 쓰므로 안 쓸 때는 `notebook`과 PVC를 지우는 편이 좋다(리모트 가용 메모리 약 7GiB).
  - 모임장 2026 핸즈온(전체 Kubeflow 26.03.1)에서는 `Notebook` CR + PodDefault `mlflow-access`(MLflow·오브젝트 스토리지 접속 정보), `access-ml-pipeline`(KFP API 토큰)로 같은 효과를 내고, 파드가 2/2인 것은 Istio 사이드카 때문이다. KFP 용어: Pipeline(DAG 청사진) / Pipeline Version(불변 판본) / Run(1회 실행) / Experiment(Run 묶음) / Recurring Run(Cron 스케줄).
  - 실패 원인 확인: `submit.py` 출력의 FINAL과 태스크별 로그, `kubectl get workflow -l pipeline/runid=<run_id> -o json`의 드라이버 메시지(annotations 초과), 파드 이벤트(argument list too long), MLMD는 `kubectl exec deploy/mysql -- mysql`로 `metadb.Artifact` 조회.
- 도전과제: K8s 고급 스케줄링(어피니티·톨러레이션) 실습 따라해 보기.
