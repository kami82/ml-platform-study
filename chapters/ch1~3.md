# CH1. MLOps와 ML 엔지니어링 시작

### 한 줄 요약

ML 프로젝트는 한 번 배포하고 끝나는 일이 아니라 실험과 운영을 오가며 반복되는 수명주기이고, 이를 안정적으로 돌리려면 파이프라인 자동화·피처 스토어·모델 레지스트리·배포 자동화를 갖춘 ML 플랫폼이 필요하다.

<br>

### 주요 내용

**1. 머신러닝 수명주기는 두 단계로 나뉜다**

- **실험 단계**: 문제 정의는 파이프라인 바깥의 사람 단계이고, 파이프라인 안은 탐색적 데이터 분석(EDA) → 데이터 수집·준비 → 데이터 버전 관리 → 모델 훈련 → 모델 평가 → 모델 검증이다. 그림의 되돌아가는 화살표가 핵심이다. 모델 평가에서 데이터 수집·준비와 모델 훈련으로, 모델 검증에서 모델 훈련으로 복귀한다. 즉 평가·검증이 실패하면 코드가 아니라 데이터나 훈련으로 돌아가므로, 처음부터 단계를 하나의 오케스트레이션 파이프라인으로 묶어 자동화한다.
- **개발/스테이징/프로덕션 단계**: 실험 단계의 파이프라인을 완전히 자동화하고 끝에 **모델 배포**를 붙인다. CI 등이 트리거가 되어 파이프라인이 돌고, 결과물은 보통 REST API 형태의 ML 서비스다. 여기에 **모니터링**과 **재훈련**이 더해져 성능이 임계값 아래로 떨어지면 파이프라인이 다시 실행된다.
- 실험이 끝나는 것은 아니지만, 이 시점부터 보안·확장성·견고성·실시간 성능·윤리적 제약이 우선순위로 올라온다.

**2. 각 단계의 핵심 포인트**

- **문제 정의**: 첫 질문은 "정말 ML이 필요한가". 휴리스틱(사람이 정한 규칙)으로 충분하면 ML을 쓰지 않는다. 휴리스틱을 baseline으로 먼저 만들고, ML이 그걸 비즈니스 지표에서 의미 있게 넘어야 운영 비용이 정당화된다.
- **데이터 수집·준비**: 실제 데이터가 부족하면 합성 데이터를 고려하고, 애노테이션으로 레이블을 붙인 뒤 훈련·검증·테스트로 나눈다. 시간 순서가 있는 데이터는 시간 기준으로 나눠 미래 정보 누수를 막는다.
- **데이터 버전 관리**: ML에서는 코드뿐 아니라 데이터가 바뀌어도 동작이 바뀐다. 재현성을 위해 데이터도 버전 관리해야 하지만, Git처럼 표준이 된 도구는 아직 없다.
- **훈련**: 데이터셋과 전략이 정해지면 자동화할 수 있고, 자동화하면 파라미터와 아티팩트가 추적되어 재현성이 생긴다. 저자들은 훈련이 생각보다 시간을 덜 차지한다고 본다.
- **평가 vs 검증**: 평가는 훈련에 쓰지 않은 데이터로 정밀도·재현율·AUC 등을 재는 것, 검증은 개발팀이 아닌 비즈니스 이해관계자가 "기대대로 동작하는가"를 확인하는 것.
- **배포**: REST API → 컨테이너화 → 클라우드 배포가 기본 경로. 이후 부하 테스트, 오토스케일링, 버전 관리, 롤백 전략까지 준비한다.
- **모니터링**: 시스템 지표(RPS, HTTP 상태 코드), ML 지표(데이터·모델 드리프트), 비즈니스 지표(이탈률, 유지율)를 함께 본다.
- **재훈련**: 정해진 주기나 임계값 이벤트로 트리거하고, 훈련뿐 아니라 배포까지 자동화해야 의미가 있다.

**3. ML 엔지니어에게 필요한 역량**

- 실제 소프트웨어 시스템을 배포·디버깅해 본 엔지니어링 역량
- 역전파까지는 몰라도 되지만 PyTorch, TensorFlow, scikit-learn 같은 프레임워크를 다루고 새 도구를 빨리 익히는 능력
- 데이터 엔지니어링 역량(가장 어려운 건 결국 양질의 데이터 확보)
- 자동화와 실험 재현성에 대한 감각. 규제·감사 대상일수록 재현성이 결정적이다.
- 한꺼번에 다 갖출 필요는 없고, 문제를 작게 쪼개 하나씩 익히면 된다.

**4. ML 플랫폼 구축**

- 책은 쿠버네티스 위에 **Kubeflow**를 설치하는 것에서 시작해 플랫폼을 점진적으로 확장한다. 같은 아키텍처 그림을 매 장 반복하며 다루는 컴포넌트를 강조하는 방식(인프라는 알파벳, 데이터 컴포넌트는 숫자 태그).
- 그림 1.4의 태그. 이후 장에서 "이번 장은 D와 4를 다룬다" 식으로 대응된다. 점선 원이 플랫폼 경계이고 외부 데이터 소스와 사용자는 바깥에 있다.

  | 분류 | 컴포넌트 |
  | :--- | :--- |
  | 사람 중심 단계 | 1 문제 정의 및 설계, 2 모델 설계 |
  | 파이프라인 컴포넌트 (A 오케스트레이션 안) | 3 데이터 수집/준비, 4 모델 훈련, 5 모델 평가 및 검증, 6 모델 배포 |
  | 리니지·추적성 | C 실험 추적, 8 모델 모니터링 |
  | 데이터·모델 저장 | 9 데이터 웨어하우스, D 피처 스토어, B 모델 레지스트리 |
  | 고객 대면 | E 모델 API, 7 사용자 |

- 피처 스토어는 데이터 수집, 모델 훈련, 모델 API 세 곳에 같은 피처를 공급해 훈련-서빙 불일치를 막는다. 모델 훈련은 파라미터·지표를 실험 추적에, 훈련된 모델을 레지스트리에 보내고 레지스트리가 평가와 배포에 모델을 돌려준다. 모델 API의 로깅은 모델 모니터링으로 가고 모니터링은 다시 문제 정의로 돌아간다. 모델 API의 스트리밍 데이터는 데이터 웨어하우스로 되돌아가 다음 훈련 데이터가 된다.
- 데이터 웨어하우스·레이크, 배치/스트리밍 처리기 같은 일반 데이터 시스템은 플랫폼 경계 밖으로 보고 간단히만 다룬다.
- SageMaker·Vertex AI 같은 관리형 플랫폼이 있어도 직접 조립해 보는 경험이 도구 간 연결과 한계 극복을 이해하는 데 가치가 있다는 입장.
- 모든 상황에 맞는 단일 아키텍처는 없다. 도구 선택도 정답이 아니라 출발점이며, 며칠 PoC로 직접 확인하길 권한다.
- 이 기반은 12~13장에서 벡터 DB, 가드레일, 비용 최적화, 프롬프트 관리를 더해 **LLMOps**로 확장된다. LLMOps는 기존 루프를 대체하지 않고 세 지점에만 접속한다(그림 1.5). 데이터 수집·준비에 RAG용 문서가 들어오고, LLM 생성의 로깅이 기존 모델 모니터링으로 합류하며, 사용자와 모델 API 사이에 입력·출력 가드레일이 끼어든다. 모델 훈련·레지스트리·실험 추적은 LLM 쪽과 연결선이 없다. 훈련 대신 프롬프트 관리, 모델 라우팅, 시맨틱 캐싱이 그 자리를 맡는다.

<br>

| 개념 | 설명 |
| :--- | :--- |

| 데이터 버전 관리 | 데이터 변경도 모델 동작을 바꾸므로, 재현성을 위해 데이터에도 버전을 붙이는 것 |
| 오케스트레이션 파이프라인 | 수명주기 단계를 하나의 자동화된 흐름으로 묶은 것. 책에서는 Kubeflow Pipelines |

| 훈련-서빙 불일치(skew) | 훈련 때와 서빙 때 데이터 변환이 달라 성능이 떨어지는 현상. 피처 스토어로 줄인다 |
| 모델 레지스트리 | 모델·하이퍼파라미터·플롯·메타데이터를 기록하고 스테이징→프로덕션 승격을 관리. 책에서는 MLflow |
| 가중치 vs 하이퍼파라미터 | 가중치는 학습 중 갱신되는 값, 하이퍼파라미터는 학습 전에 사람이 정하는 설정(학습률, 에폭 등) |
| 모델 배포 자동화 | CI/CD가 컨테이너를 빌드해 레지스트리에 푸시하고, 쿠버네티스 매니페스트로 서비스를 갱신하는 흐름 |
| 데이터/모델 드리프트 | 운영 데이터나 입력-출력 관계가 훈련 때와 달라져 성능이 떨어지는 현상 |

## 실무 사례

> ⚠️ 가상 사례 — 카드사 이상 거래 탐지 서비스에 1장의 수명주기를 적용해 본 시나리오입니다.

**상황과 문제**

카드사 이상 거래 탐지팀이 노트북에서 만든 모델을 엔지니어가 서빙 코드로 다시 옮겨 배포했다. 배포 후 오탐이 크게 늘었는데, 원인을 찾아보니 "최근 7일 평균 결제액" 피처를 훈련 코드와 서빙 코드가 서로 다른 기준으로 계산하고 있었다. 어떤 데이터와 설정으로 학습한 모델인지도 기록이 없어 이전 모델로 되돌리기도 어려웠다.

<br>

**적용 방법**

1. 규칙 기반 1차 차단(금액이 평소의 5배 이상이고 해외 결제면 검토)을 baseline으로 두고 ML 모델이 이를 넘는지부터 측정한다.
2. 피처 정의를 피처 스토어로 옮겨 훈련(오프라인)과 서빙(온라인)이 같은 정의를 쓰게 하고, 시점 기준 조회로 미래 정보 누수를 막는다.
3. 훈련 실행마다 데이터 버전, 코드 커밋, 하이퍼파라미터, 평가 지표를 MLflow에 기록하고, 레지스트리에서 스테이징→프로덕션으로 승격한다.
4. 배포는 CI/CD로 자동화하고, RPS·에러율과 함께 입력 분포 드리프트를 모니터링해 임계값을 넘으면 재훈련을 트리거한다.

<br>

**결과 또는 기대 효과**

- 기대 효과: 훈련-서빙 불일치로 인한 성능 저하 감소, 문제 발생 시 이전 모델로 빠른 롤백, 원인 추적 시간 단축
- 확인된 결과: 없음(가상 사례)

# CH2. MLOps란 무엇인가

### 한 줄 요약

ML의 가치는 모델 하나가 아니라 계속 개선되는 폐쇄 루프에서 나오며, MLOps는 데이터·모델·실험이라는 DevOps에 없는 요소까지 자동화하고 추적해 이 루프를 지속 가능하게 만드는 일이다.

<br>

### 주요 내용

**1. ML은 루프로 생각해야 한다**

- 대부분의 기업은 모델을 새로 연구하지 않고 기존 아키텍처를 재사용한다. 진짜 어려운 질문은 그 다음이다: 어떻게 훈련하고, 데이터를 어떻게 넣고, 다른 서비스와 어떻게 연결하고, 어디서 실행하고, 정확도를 어떻게 유지할 것인가.
- 모델·데이터·하이퍼파라미터는 일시적이고, 시간이 흐르며 진화하는 루프의 일부로 봐야 한다. 그래야 모델이 바뀔 때를 대비한 프로세스를 처음부터 설계하게 된다.
- **모델(가중치+네트워크)**과 **코드(아키텍처 정의+지원 코드)**는 별개로 버전이 움직인다. 둘이 어느 버전끼리 짝인지 알려 주는 것이 **리니지**다.

**2. 루프의 7단계**

1. **문제 정의**: "이탈률을 예측하라" 수준으로는 부족하다. 비즈니스·기술·법무 이해관계자별 핵심 질문(성공 지표, 허용 오차, 컴퓨팅 리소스, 재훈련 트리거, 개인정보·거버넌스)에 함께 답해야 범위와 산출물이 명확해진다.
2. **데이터 수집**: 이후 모든 단계가 여기서 생긴 편향을 이어받는다. 관련성, 적정 크기, 품질, 편향·누수 방지, 배포 환경을 대표하는 분포, 다양성, 리니지를 갖춰야 한다. 연구는 정제된 공개 데이터셋을 전제하지만 기업은 도메인 데이터를 직접 만들어야 하는 경우가 많다. 리니지는 초기에 자주 생략되는데, 이는 일종의 기술 부채다. 리니지가 있으면 데이터 오류 수정이 스크립트 재작성 대신 쿼리 하나로 끝날 수 있다.
3. **EDA**: 스키마, 분포와 클래스 균형, 피처 품질과 계산 비용, 주기성, 이상값을 확인한다. 다변량 분석과 PCA·t-SNE 같은 차원 축소를 활용한다. 모든 가정은 검증 전까지 리스크로 보고, 파이프라인 초기에 검증 장치를 둔다.
4. **모델링과 훈련**: 문제 유형(분류·탐지·회귀)과 데이터에 맞는 모델을 고른다. 모델·데이터 버전 관리, 실험 추적, 훈련 파이프라인, 하이퍼파라미터 탐색이 공통으로 겨냥하는 건 리니지·추적성·수작업 제거다. 코드·설정·데이터를 분리한 **모듈식 코드베이스**로 만들면 모델 크기 조정 같은 실험이 설정 수정만으로 가능하다. 단, 과도한 파라미터화는 피하고 단순하게 시작한다.
5. **평가**: 지표 선택은 문제 정의와 연결된다. 분류·탐지는 정밀도·재현율·F1, 회귀는 MAE·MSE. 의료는 위양성에, 금융은 재현율에 더 엄격할 수 있다. 홀드아웃 데이터셋은 운영 데이터를 닮게 만들고, 자동 평가하며, 훈련 데이터만큼 엄격하게 버전 관리한다. 분할이 바뀌면 누수가 생겨 재평가·재훈련이 필요하다. 오분류 패턴 분석, 적대적 테스트, 에지 케이스 시뮬레이션도 이 단계에 포함된다.
6. **배포**: 마이크로서비스 엔드포인트 또는 에지 디바이스 배포. 최적화(양자화 등) 후의 최종 모델로 다시 성능을 테스트해야 한다. 스테이징에서 비교 검증 후 프로덕션으로 승격하고, 롤백이 쉬워야 한다. 책에서는 BentoML, Yatai, Chainlit을 쓴다.
7. **모니터링과 유지보수**: 데이터 모니터링(드리프트), 성능 모니터링, 오류 모니터링. 알림이 담당자에게 닿지 않으면 지표가 없는 것과 같다. 드리프트 탐지와 재훈련 트리거에 Evidently를 쓴다. 유지보수는 마지막 단계라기보다 루프 전체에 분산되어 있다.

**3. MLOps가 어려운 이유**

- 루프의 블록 하나하나가 전문 영역이고, 데이터 보안·프라이버시·공정성이 복잡도를 더한다.
- 데이터 과학자(정밀도·재현율)와 ML 엔지니어(지연 시간·스케일링)의 언어가 다르다.
- 최적화와 스케일링은 뒤로 밀리기 쉽지만 운영에서 치명적이다.
- 지저분한 실세계 데이터, 거버넌스·설명 가능성 요구, 도구 파편화(모델 레지스트리만 10개 이상).
- 그래서 작은 팀은 MLOps를 건너뛰기 쉽지만, 장기적으로는 큰 기술 부채가 된다.

**4. 성숙한 조직에서 MLOps의 이점**

실험 가속, 비용 최적화(사일로 제거), 팀 간 협업, 효율성(반복 작업 자동화), 반복성·추적성, 스케일링. 핵심은 "좋은 관행을 기본값으로 만들어 진입 장벽을 낮추는 것"이다.

**5. DevOps vs MLOps**

- 공통점: 자동화 지향, CI/CD, 다학제적 협업
- 차이점: MLOps는 데이터를 핵심 컴포넌트로 다루고, 코드 변경 없이도 모델이 변하므로 **지속적 훈련(CT)**이 필요하며, 해석 가능성·편향, 입력 변화에 따른 성능 저하 모니터링, 빌드가 아닌 **실험 자체의 추적**을 다룬다.

**6. 구글 기준 MLOps 성숙도**

- **Level 0**: 수동 스크립트, 모니터링 없음, 드문 릴리즈
- **Level 1**: 모델이 아니라 **재훈련 파이프라인 전체**를 배포. 개발·운영에서 같은 파이프라인을 쓰는 실험-운영 대칭성. 데이터·모델 검증, 피처 스토어, 파이프라인 메타데이터, 자동 트리거가 필요
- **Level 2**: 파이프라인 자체의 빌드·배포까지 CI/CD로 자동화. 데이터·모델 분석 외에는 거의 자동화되고 파이프라인을 조직 전체가 함께 관리

<br>

### 핵심 개념

| 개념 | 설명 |
| :--- | :--- |
| ML 루프 | 문제 정의 → 데이터 수집 → EDA → 훈련 → 평가 → 배포 → 모니터링·유지보수가 다시 앞으로 이어지는 폐쇄 루프 |
| 리니지 | 원천 데이터부터 배포 모델까지 "무엇으로 어떻게 만들었는가"를 잇는 계보. 유지(기록)와 추적(조회)이 한 세트 |
| 큐레이션 | 수집한 원시 데이터를 선별·정제·균형 조정·문서화해 모델링용 데이터셋으로 만드는 작업 |
| 유해한 편향 / 데이터 누수 | 편향은 데이터가 현실과 다른 문제, 누수는 평가가 현실과 다른 문제. 둘 다 데이터 단계에서 막아야 한다 |
| EDA | 데이터의 스키마·분포·이상값·피처 품질을 탐색해 가정을 검증하는 단계 |
| 모듈식 코드베이스 | 코드·설정·데이터를 분리하고 모델을 그 조합의 아티팩트로 보는 구조. 실험 속도와 재현성을 높인다 |
| 홀드아웃 데이터셋 | 학습에 절대 쓰지 않는 최종 평가용 데이터. 운영 데이터를 닮게 구성하고 버전 관리한다 |
| 정밀도 / 재현율 / F1 | 예측한 것 중 맞은 비율 / 실제 정답 중 찾아낸 비율 / 둘의 조화평균 |
| 지속적 훈련(CT) | 코드 변경 없이 데이터 변화에 맞춰 모델을 재훈련하는 것. MLOps가 DevOps와 갈리는 지점 |
| 실험-운영 대칭성 | 개발 환경과 프로덕션 환경이 같은 파이프라인을 쓰는 것. 성숙도 Level 1의 특징 |

## 실무 사례

> ⚠️ 가상 사례 — 의료 영상 AI 플랫폼에 2장의 루프와 평가 원칙을 적용해 본 시나리오입니다.

**상황과 문제**

의료 영상 판독 보조 모델을 병원 A 데이터로 학습해 배포했는데, 병원 B에 확장 배포하자 민감도가 눈에 띄게 떨어졌다. 확인해 보니 병원 B는 촬영 장비 제조사와 프로토콜이 달라 영상의 밝기 분포가 달랐고(데이터 드리프트), 학습 데이터셋에는 병원 A 장비 영상만 들어 있었다(표본 편향). 어떤 데이터 버전으로 학습했는지 기록도 흩어져 있어 원인 파악에 시간이 오래 걸렸다.

<br>

**적용 방법**

1. 문제 정의 단계에서 임상·법무 이해관계자와 함께 허용 위음성률, 개인정보 처리 기준, 재훈련 트리거 지표를 합의한다. 의료 도메인이므로 놓치는 사례를 줄이는 방향(재현율·민감도)을 우선 지표로 둔다.
2. 데이터 수집 시 병원·장비·프로토콜별 분포를 EDA로 확인하고, 그룹별 성능을 따로 측정하도록 홀드아웃 데이터셋을 구성한다.
3. 데이터셋 버전, 전처리 코드 커밋, 설정, 평가 지표를 실험 추적 도구에 기록해 모델별 리니지를 남긴다.
4. 운영 중 입력 분포를 모니터링해 기관·장비별 드리프트를 감지하면 알림과 함께 재훈련 파이프라인을 트리거한다(성숙도 Level 1 목표).

<br>

**결과 또는 기대 효과**

- 기대 효과: 신규 기관 확장 전에 성능 저하를 미리 감지, 원인 추적 시간 단축, 규제 대응 시 학습 데이터 출처 설명 가능
- 확인된 결과: 없음(가상 사례)

# CH3. 쿠버네티스 위에 애플리케이션 구축하기

### 한 줄 요약

ML 엔지니어의 핵심 책임 중 하나는 ML 시스템을 떠받치는 인프라를 만들고 유지하는 것이며, 3장은 FastAPI 앱 하나를 도커 패키징 → 쿠버네티스 배포 → CI/CD 자동화 → 프로메테우스/그라파나 모니터링까지 끌고 가면서 ML 플랫폼의 토대가 되는 DevOps 기본기를 실습한다.

<br>

### 주요 내용

**1. 3장의 위치와 목표**

- 1~2장이 개념과 조직 관점이었다면 3장부터 실습이다. 멘탈 맵의 초점이 ML 플랫폼의 기반인 쿠버네티스, CI/CD, 모니터링으로 옮겨간다.
- 전체 흐름: 도커로 앱과 의존성을 컨테이너로 패키징 → 쿠버네티스가 리소스 관리·스케일링·재생성을 담당 → CI(GitLab CI)와 CD(Argo CD)로 배포를 자동화 → 프로메테우스(지표 수집)와 그라파나(시각화)로 모니터링.
- 도구는 수단이다. 자동화된 ML 플랫폼이라는 목표를 이룰 수 있다면 어떤 도구를 써도 무방하다. 4~5장에서 피처 스토어, ML 파이프라인, 실험 추적, 드리프트 모니터링 같은 MLOps 도구로 범위를 넓힌다.
- 실습 앱은 무작위 농담을 반환하는 FastAPI 엔드포인트 하나(hello-joker)다. 코드는 https://github.com/practical-mlops/chapter-3.

**2. 도커 (3.2)**

- `main.py`(FastAPI + pyjokes)와 `requirements.txt`가 전부다. 로컬에서는 Uvicorn(ASGI 서버)으로 8083 포트에서 실행한다.
- Dockerfile 구성: 베이스 이미지 → 작업 디렉터리 → `requirements.txt`를 먼저 복사해 의존성 설치(레이어 캐시 활용) → 소스 복사 → `EXPOSE 8083` → `PYTHONPATH` 환경 변수 → `entrypoint.sh`(uvicorn 실행)를 ENTRYPOINT로 지정.
- 빌드 → 실행(`-p 8081:8083`) → Docker Hub 로그인 → 태그 → 푸시. 이미지 태그는 버전이나 깃 커밋 ID를 쓴다. 컨테이너 레지스트리는 이미지를 저장·관리하는 중앙 리포지터리이고, 서버는 여기서 이미지를 받아 컨테이너로 실행한다.
- 실습 메모: 책의 `python:3.10-slim-buster`는 Debian buster 지원 종료로 apt 저장소가 404를 반환해 빌드가 실패한다. `slim-bookworm`으로 교체하면 나머지 단계는 그대로 동작한다. 책과 코드 저장소의 Dockerfile에는 `ARG environment` / `ENV ENVIRONMENT` 줄이 누락되어 있다. `docker buildx`로 amd64·arm64 멀티 아키텍처 이미지를 한 번에 빌드할 수 있다.

**3. 쿠버네티스 (3.3)**

- 아키텍처: 마스터 노드(API 서버, etcd, 스케줄러, 컨트롤러)와 워커 노드(컨테이너 런타임, kubelet). 사용자는 마스터의 API 서버에 명령을 전달하고, 마스터가 워커 노드에 실행을 지시한다.
- 설치: 책은 K8s 1.24(Kubeflow 1.7 지원 버전). 스터디는 Gitea Runner 최소 지원 버전 때문에 1.29를 쓴다. Linux/WSL2는 K3s(traefik 비활성화, flannel host-gw), macOS는 kind(NodePort 30000~30003 포트 매핑).
- 객체 계층: **Pod**(컨테이너를 담는 최소 실행 단위, `port-forward`로 접근) → **ReplicaSet**(selector의 레이블과 일치하는 파드를 감시해 `replicas` 수를 유지, 파드를 지우면 다시 만들고 `scale`로 늘림) → **Deployment**(ReplicaSet을 생성·관리, 이미지 태그를 바꾸면 새 ReplicaSet을 올리고 이전 것을 0으로 내리는 롤링 업데이트, `rollout undo`로 롤백).
- 서비스: 파드 집합에 대한 안정적인 접근 추상화. **NodePort**는 노드 IP의 30000번대 포트로 외부 노출, **ClusterIP**는 클러스터 내부 전용(서비스명으로 DNS 호출), **LoadBalancer**는 외부 LB가 EXTERNAL-IP를 부여(K3s는 내장 klipper-lb가 노드 IP를 할당).
- Helm: 쿠버네티스 패키지 매니저. 차트 = 템플릿 + `values.yaml`. `helm create`로 뼈대를 만들고 values의 `replicaCount`, `image.repository/tag`, `service.type/port`만 고쳐 네임스페이스에 설치·삭제한다.
- 결론: ML 애플리케이션은 동적이고 리소스를 많이 소모하므로 K8s의 배포·확장·관리 속성과 특히 잘 맞는다.
- 실습 메모: 책의 `port-forward` 포트 표기는 오타이며 `8080:8083`이 맞다.

**4. CI/CD (3.4)**

- CI의 목표는 테스트를 거친 뒤 배포를 자동화하는 것. 깃 커밋마다 트리거되며 전형적 용도는 코드 테스트, 도커 이미지 빌드, 배포 트리거다.
- 책의 파이프라인(`.gitlab-ci.yml`)은 3단계다. **test**(pytest) → **build**(docker build, 태그는 커밋 SHA 앞 8자리, Docker Hub 푸시) → **update**(yq로 헬름 차트 `values.yaml`의 `image.tag`를 새 태그로 바꿔 `[skip ci]` 커밋으로 다시 푸시). 자격증명(`DOCKER_USERNAME`, `DOCKER_PASSWORD`, 깃 액세스 토큰)은 CI/CD Variables/Secrets로 주입한다.
- 스터디는 GitLab 대신 **Gitea + Gitea Actions**(GitHub Actions 호환)를 로컬 클러스터에 Helm으로 설치했다. 러너 파드는 reach-gitea init 컨테이너(Gitea 응답 대기) → **dind** 사이드카(Docker 데몬, privileged) → **runner** 컨테이너(Gitea에 등록 후 잡 실행)로 구성된다. runner와 dind는 emptyDir의 `docker.sock`을 공유하고, 잡 컨테이너와 `docker build`는 모두 dind 안에서 실행된다. privileged는 실습용으로만 허용하고 운영에서는 rootless dind나 Kaniko를 검토한다.
- GitLab → Gitea Actions 변환 포인트: stages → jobs + `needs`로 순서 지정, `CI_COMMIT_SHA` → `github.sha`(짧은 해시는 `cut`으로 자름), `CI_PROJECT_DIR` + clone → `actions/checkout`, `docker login -p` → `--password-stdin`, 트리거를 `main` 푸시로 제한(update 잡이 main에 푸시하므로 `[skip ci]`가 없으면 무한 루프), `apt-get install -y`.
- **Argo CD**: Git을 유일한 진실의 원천으로 두고 Git의 매니페스트와 K8s에 배포된 상태를 지속 감시해 동기화한다. `Application` 리소스에 source(Gitea 저장소의 hello-joker 차트 경로와 `values.yaml`), destination(`online-ml-svc` 네임스페이스), syncPolicy(automated, selfHeal, CreateNamespace)를 선언하면, CI가 `values.yaml`의 태그를 바꿀 때마다 Argo CD가 새 이미지를 자동 배포한다(GitOps).
- 실습 메모: httpx 0.28.1에서 테스트가 실패해 `httpx==0.27.2`로 고정했다.

**5. 모니터링 (3.5)**

- 구조: 애플리케이션이 `/metrics` 엔드포인트를 노출 → 프로메테우스가 주기적으로 스크랩 → 그라파나가 시각화 → Alertmanager가 지표를 보고 알림 채널(이메일 등)로 라우팅.
- 설치: `prometheus-community/prometheus`(NodePort 30002)와 `grafana/grafana`(NodePort 30003, 데이터소스로 프로메테우스 등록)를 Helm으로 설치.
- 앱 계측: starlette_exporter의 `PrometheusMiddleware`와 `/metrics` 라우트를 추가하면 요청 수·응답 시간 같은 기본 지표가 제공된다. `prometheus_client`의 `Counter`로 커스텀 지표를 추가할 수 있다(이름 뒤에 `_total`이 붙고, 기본 레지스트리를 공유해 `/metrics`에 함께 노출).
- 수집 대상 등록: 헬름 values의 `podAnnotations`에 `prometheus.io/scrape`, `prometheus.io/path`, `prometheus.io/port`(8083)를 넣고 Git에 푸시하면 Argo CD가 반영하고, PromQL `starlette_requests_total`로 수집을 확인한다.

**6. 책 vs 스터디 실습 환경**

| 교재 | 스터디 | 이유 |
| :--- | :--- | :--- |
| `python:3.10-slim-buster` | `python:3.10-slim-bookworm` | buster EOL로 `apt-get update`가 404 |
| GitLab + GitLab Runner | Gitea + Gitea Actions(act_runner, dind) | 로컬 클러스터에 설치형으로 구성 |
| Docker Hub | Docker Hub 그대로 | Harbor 등 다른 레지스트리는 도전과제 |
| K8s 1.24 | K3s 1.29 / kind 1.29 | Gitea Runner 최소 지원 버전이 K8s 1.29 |

**7. (참고) Kustomize**

- 템플릿이나 DSL 없이 표준 YAML을 관리하는 선언적 도구로, `kubectl -k`에 내장되어 있다.
- `configMapGenerator` / `secretGenerator`로 프로퍼티·env 파일이나 리터럴에서 ConfigMap·Secret을 생성한다. 이름에 내용 해시 접미사가 붙어 설정이 바뀌면 새 객체가 만들어지고 롤링 업데이트가 유발된다(`generatorOptions.disableNameSuffixHash`로 비활성화 가능).
- 공통 필드 일괄 적용(`namespace`, `namePrefix/nameSuffix`, `labels`, `commonAnnotations`), `patches`(strategicMerge, Json6902), `images`(이미지 이름·태그 교체), `replacements`(다른 객체의 필드 값 주입)를 제공한다.
- **베이스**(공통 리소스 + kustomization.yaml)와 **오버레이**(베이스를 참조해 환경별 패치를 겹침) 구조로 dev/staging/prod를 관리한다. Helm은 템플릿화된 필드만 바꿀 수 있지만 Kustomize는 유효한 YAML 위에 작은 패치를 겹치는 방식이다.

| 개념 | 설명 |
| :--- | :--- |
| 컨테이너 / 이미지 / 레지스트리 | 앱과 의존성을 묶은 격리 실행 단위 / 그 원본이 되는 읽기 전용 패키지 / 이미지를 저장·배포하는 중앙 저장소 |
| 마스터 노드 / 워커 노드 | API 서버·etcd·스케줄러·컨트롤러로 클러스터를 관리하는 노드 / 컨테이너 런타임과 kubelet으로 실제 파드를 실행하는 노드 |
| Pod → ReplicaSet → Deployment | 최소 실행 단위 → 레이블 selector로 파드 수를 유지 → ReplicaSet을 관리하며 롤링 업데이트·롤백을 제공 |
| Service(NodePort / ClusterIP / LoadBalancer) | 파드 집합에 대한 고정 접근점. 노드 포트로 외부 노출 / 클러스터 내부 전용 / 외부 LB로 EXTERNAL-IP 부여 |
| Helm 차트 | 템플릿 + values.yaml로 K8s 앱을 패키징해 설치·업그레이드를 단순화하는 패키지 매니저 단위 |
| CI 스테이지 / 잡 | 파이프라인의 단계(test → build → update)와 그 안에서 실행되는 작업. 한 스테이지의 잡은 동시에 실행 |
| dind(Docker-in-Docker) | CI 러너 파드 안에서 Docker 데몬을 사이드카로 띄워 이미지를 빌드하는 방식. privileged가 필요 |
| GitOps / Argo CD | Git을 유일한 진실의 원천으로 두고 Git 상태와 클러스터 상태를 지속 동기화하는 배포 방식과 그 도구 |
| 익스포터 / 스크레이핑 | 앱 지표를 /metrics로 노출하는 라이브러리 / 프로메테우스가 그 엔드포인트를 주기적으로 긁어 오는 동작 |
| Kustomize 베이스 / 오버레이 | 공통 매니페스트 묶음 / 베이스를 참조해 환경별 패치를 덧씌우는 디렉터리 |

## 실무 사례

> ⚠️ 가상 사례 — 의료 영상 AI 추론 서비스에 3장의 인프라 기본기를 적용해 본 시나리오입니다.

**상황과 문제**

추론 서버를 GPU 서버에 직접 설치해 운영하다 보니, 서버마다 CUDA·라이브러리 버전이 달라 "내 서버에선 되는데" 문제가 반복되고, 트래픽이 몰리면 수동으로 서버를 늘려야 한다. 배포는 사람이 SSH로 들어가 파일을 바꾸는 방식이어서 지금 어떤 버전이 떠 있는지 Git과 맞지 않는 경우가 생긴다.

<br>

**적용 방법**

- 추론 서버를 Docker 이미지로 패키징해 실행 환경을 고정하고, 커밋 해시를 태그로 레지스트리에 저장한다.
- Kubernetes Deployment로 배포하고 Service로 엔드포인트를 노출하며, 레플리카 수로 확장하고 롤링 업데이트·롤백을 활용한다.
- CI가 테스트 → 이미지 빌드·푸시 → 헬름 values의 태그 갱신까지 수행하고, Argo CD가 Git의 values를 감시해 클러스터에 자동 반영한다(GitOps).
- 추론 서버에 /metrics를 노출해 RPS, 지연 시간, HTTP 상태 코드, GPU 사용률을 프로메테우스로 수집하고 그라파나로 본다.

<br>

**결과 또는 기대 효과**

- 기대 효과: 환경 불일치 제거, Git과 실제 배포 상태의 일치, 배포·롤백 속도 향상, 부하에 따른 확장과 장애 시 자동 복구, 이후 Kubeflow 등 ML 컴포넌트를 올릴 기반 확보.
- 확인된 결과: 없음 (가상 시나리오)
